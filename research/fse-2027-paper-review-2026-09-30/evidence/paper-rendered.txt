6     Trace links between software architecture artifacts and code support impact analysis, change propagation,
7     and compliance review, yet they are the hardest to recover: the artifacts describe the system on a higher
8       level of abstraction and rarely directly match the names in the code. Lexical recovery overlooks aliases and
9       implicit references, while a per-sentence Large Language Model (LLM) rebuilds that knowledge on every call
      and accepts plausible-but-wrong links. We present ArchLinker, a multi-stage LLM workflow for architecture
10
      document-architecture model traceability link recovery that keeps shared alias knowledge separate from
11
     two recovery routes. The first stage derives an alias table over the document and component set. The two
12
       routes then generate candidates from written names or references to earlier sentences, derive evidence for
13     each candidate, and apply a route-specific judge. One judge handles all written-name forms, while another
14     judge handles resolved references. On five open-source benchmark projects, we evaluate ArchLinker against
15     the state of the art. ArchLinker improves performance in comparison to the strongest baseline, run on the
16    same LLM backend, by 13 percentage points (pp) in architecture doc-model average F1, and by 13 pp in the
17     recall-weighted average F2. This gain carries through to 7 pp of average F1 on the downstream doc-code task.
18    Under an architecture-driven suite that adds per-component measures, the gap widens to 30 and 28 pp. A
19     replication package provides prompts, code, raw LLM responses, and per-project results.
20     Additional Key Words and Phrases: Documentation, large language models, natural language processing,
21     software architecture, software maintenance, traceability

23    1  INTRODUCTION
24
     Beyond code, software systems are described by architecture documentation and architecture
25
      models. Trace links tie these artifacts together, so a change in one can be followed into the others.
26
     They support impact analysis, change propagation, and compliance review, and without them
27
      architectural knowledge erodes as the system ages [17, 32, 46]. Recovering these links automat-
28
       ically is a long-standing open problem. Recent LLM-based approaches show success, with the
29
      strongest reaching 84% F1 [30]. However, can practitioners rely on these links? On an established
30
     benchmark [28], we found that doc-code gold links are highly concentrated across components: the
31
      three largest components hold 69.3–99.3% of component-code links. A tool can therefore top the
32
     benchmark yet never link a whole component that the documentation describes, and the score fails
33
       to present this miss sufficiently. This paper answers the question with both an improved traceability
34
       link recovery method and a measure that exposes these misses.
35
      We study this in architecture traceability: linking a documentation sentence to model components
36
      (doc-model), and through them to code (doc-code). Prior work follows two lines. The lexical line,
37
     such as SWATTR [39], scores each candidate link with linguistic patterns. The LLM line, such
38
      as LiSSA [29], classifies each documentation-and-target pair with one LLM call. The strongest
39
      approach, Artemis, combines lexical and LLM technique, uses an LLM to extract architecture
40
       entities with their aliases, then matches them to the model by name and embedding similarity [30].
41
      In practice, these approaches both miss true links and produce false ones. Components whose
42
      documentation never uses their model name receive few or no links, and components whose name
43
      overlaps with common words receive links the text does not support. Furthermore, we found
44
      that on the benchmark, baselines abandon up to 7.1% of documented components entirely. These
45
      approaches share one root cause: they mainly treat word overlap as the signal for a link. SWATTR

55    A trace link between an architecture document and a model component is established when that
56    sentence discusses the architectural role of a component. A sentence can mention a component
57    without being about it, and be about a component without mentioning it. For example, “database
58     access” mentions DB but describes a responsibility of another component, while “It” mentions no
59    component but refers to DB through the preceding sentence (Figure 1). Our insight is that TLR is
60     therefore not about deciding whether a sentence matches a component. It is to find the specific
61    evidence in the document that supports or refutes each candidate link, and to judge the candidate
62     against that evidence.
63    We present ArchLinker, a training-free LLM workflow that recovers trace links by
64    finding and judging textual evidence. It discovers each document’s component vocabulary,
65    generates candidates through how each reference is written, and judges each candidate against
66    the evidence that produced it. Three parts work together: a shared alias-discovery stage and two
67    recovery routes, each with a candidate generator and a judge. The named-reference route uses
68    the name candidate generator to find complete names, approved aliases, and name words; the
69     coreference route uses the coreference candidate generator to resolve an implicit reference against
70      its antecedent. Each judge is a context-augmented LLM-as-a-judge: a plain judge scores an output
71     alone, but ours receives the evidence the candidate rests on, such as the matched span, how the
72    sentence writes the name, and, for an implicit reference, the antecedent sentence. So, it can reject
73     trace links the evidence does not support. Splitting the reference forms expands candidate coverage
74    without adding a second judging criterion: both written forms are judged under one rule, and what
75     separates them is a field of the evidence rather than a second rubric.
76       Percentage-point (pp) gaps below are rounded from the underlying scores. On the ArDoCo
77    benchmark[28], ArchLinker reaches a doc-model average F1 of 0.936, 13 pp above the strongest
78     baseline Artemis re-run on the same backend, and 0.955 average F2, 13 pp above it [2, 30, 38]. On
79    doc-code it reaches an average F1 of 0.879 (+7 pp) and an average F2 of 0.896 (+5 pp).
80      These gains are measured by standard link-level metrics, but do those metrics tell the full
81     story? Our second contribution starts from a measured property of doc-code links: they are highly
82    concentrated across components. On the benchmark, excluding the largest three architectural
83    components, the remaining components hold between 0.7% and 30.7% of trace links. Within each
84     project, link-level F1 pools link across components, so components with fewer links have less
85     influence on that score. If a tool misses that component entirely, the score barely moves, but
86    the architect has a gap they will not see. This makes link-level average too coarse to evaluate
87   how recovery varies for the whole architecture model. We therefore introduce an architecture-
88    driven evaluation suite that measures how recovery covers the full architecture model, not just
89    the aggregate link count (Section 4). Its key idea is to make every documented component visible
90     in the score, regardless of how many links it holds. This metric suite also revealed that although
91    Artemis improves over TransArc[30] on average, it scores lower on small components than the
92     lexical approach. In addition, it shows the strength of ArchLinker. On doc-model, ArchLinker
93    covers components that every prior tool drops. On doc-code, ArchLinker leads TransArc by 23 pp
94    on the per-component harmonic mean, against 8 pp at the link level.

     2 BACKGROUND AND MOTIVATION
128
129    2.1  Motivating Example
130  A trace link connects a documentation sentence to an architecture component (doc-model) or to
131   code (doc-code). Figure 1 uses four sentences and their links from the MediaStore benchmark.
132    Sentence 23 writes “The Database component” for what the model calls DB, and Sentence 24 refers
133   back to it only as “It”. Sentence 27 names MediaAccess and contains “database access”, but the
134    gold standard assigns no DB link because the phrase describes a responsibility rather than the
135   component. Sentence 28 then refers back to MediaAccess as “it”. The excerpt therefore shows three
136    problems: a component whose document name differs from its model name, two sentences that
137    refer to components without naming them, and a false candidate that the sentence’s evidence does
138    not support.
139     The next two subsections develop these problems in detail.

140
141    2.2  Challenges of Trace-Link Recovery
142    Lexical similarity approaches catch a link only when the sentence contains the component’s name.
143   Documentation does not always work that way. After a component is introduced, later sentences
144   can refer to it by aliases and pronouns, not by its full name. This gap between how a document
145    refers and how a name match works causes two problems: it misses true links and accepts false
146    ones.

148      Recovering these links presents three challenges shown in Figure 1.
149       (1) The document and the model can use different terms for the same component. The model
150   component is DB, but Sentence 23 writes “The Database component.” A method must discover that
151    “Database” names DB. (2) Different reference forms provide different kinds of evidence. Sentence 23
152    writes the component name via paraphrasing. Sentence 24 uses “It,” which can only be resolved
153   from the surrounding context: sentence 23 introduces DB. Likewise, Sentence 28 uses “it” for the
154   MediaAccess named in Sentence 27.
155       (3) Finding a plausible candidate does not establish a trace link.
156     Even when a sentence does refer to a component, the resolution can be wrong. A referring
157    expression such as “this” may denote an operation or a data object rather than a component. Once
158   “Database” is known as a form of DB, a match on “database access” in Sentence 27 proposes a DB
159     link. But the phrase describes a responsibility of MediaAccess, not the DB component.
160    A recovery method must therefore (i) learn document specific vocabulary to understand coined
161    terms in context, (ii) analyze references across different types of sentences, and (iii) reduce false-
162    positive links by re-evaluating candidate links.

164    2.3  Architecture-Driven Evaluation
165  We conducted an empirical study and found doc-code gold links are highly concentrated across
166   components. The components with the most links account for most link assignments, leaving
167    smaller components with little weight in link-level metrics. The standard metrics like precision,
168     recall, and F-measure averaged over all links pool links across components. Component link counts
169     differ widely, and the resulting concentration is what the standard metric can hide.
170    On JabRef, directories map to files ranging from a single file to hundreds. Three large com-
171   ponents expand into 99.3% of the gold links, while preferences component expands into only
172    0.44% (Figure 2, left axis). Link-level F1 is therefore dominated by those three. Yet 20% of the
173   documented sentences describe preferences, 46x its share of links. Similarly, 17.6% of the code’s
174    cross-component dependencies point at it, 40x its link share. A component that a reader meets in
175   one sentence out of five, and that a sixth of the code depends on, is nearly invisible to the score.

222   3  ARCHLINKER
223  We propose ArchLinker, an LLM workflow that requires no task-specific model fine-tuning or
224    labeled training data and recovers trace links between an architecture document and an archi-
225    tectural model. Its input is a document 𝐷with sentences 𝑆= {𝑠1, . . . ,𝑠𝑛} and a component set
226  𝐶= {𝑐1, . . . ,𝑐𝑚}. Its output is a link set 𝐿⊆𝑆× 𝐶. Each link (𝑠𝑖,𝑐𝑗) ∈𝐿asserts that sentence 𝑠𝑖
227   makes an architectural claim about component 𝑐𝑗as a participant in the documented system.
228      Recovering these links presents three challenges: (1) vocabulary mismatch between document
229   and model; (2) different reference forms require different evidence; (3) finding a plausible candidate
230   does not establish a trace link. A known term may serve another purpose in the sentence, and a
231    referring expression may denote an operation or data object rather than a component.
232     Design of ArchLinker. Three design decisions address the three challenges. First, ArchLinker
233    builds shared document-specific knowledge to address the vocabulary mismatch between the
234   document and model. Second, ArchLinker separates recovery into the named-reference route and
235    coreference route because different reference forms require separate tailored solutions. Third, every
236    candidate is evaluated with the evidence for that case, forming a evidence-backed judging.
237      Figure 3 organizes these decisions along two axes. The columns are three functional stages: alias
238    discovery, candidate generation, and candidate judging. The rows after alias discovery are the
239   two end-to-end recovery routes. Stage 1 builds an alias table shared by both routes. In Stage 2,
240   name candidate generator finds candidates supported by text written in the target sentence, while
241    coreference candidate generator resolves references that depend on surrounding sentences. In
242    Stage 3, name judge and coreference judge evaluate the candidates from their respective routes.
243   The workflow associates each candidate with a structured evidence bundle—the matched span, how
244    the sentence writes the component name, and for implicit references, the antecedent sentence—and

265    3.1  Alias Discovery
266    Stage 1 identifies document-specific terms that refer to model components. These terms can include
267    abbreviations, alternate names, and words of multi-word names when the document uses the word
268    for the complete component. For example, one document can write both “BigBlueButton web
269    application” and “the web app” for the model component BBB web. This stage is inspired by prior
270   work on glossary-term extraction [5, 31], software vocabulary mining [26, 35], and architecture-
271    entity extraction in Artemis [30].
272    An LLM first proposes candidate aliases from the document and component set. An internal alias
273    judge then evaluates whether the document establishes each proposed mapping. It rejects a term
274   when the term is generic vocabulary or identifies something other than one named component. If
275   an approved term maps to multiple components, ArchLinker discards the term because it does not
276    identify a unique component. The remaining mappings form the alias table used during candidate
277    generation and candidate judging. In summary, alias discovery builds one shared table that both
278    recovery routes use during candidate generation and judging.
279

280
      3.2  Named-Reference Route
281
282   The named-reference route handles candidates supported by written evidence in the target sentence.
283     Its name candidate generator combines two deterministic lexical scans. The first finds complete
284   component names and approved aliases. The second, the name-word scan, finds individual words of
285    multi-word component names even when the sentence uses a different grammatical form, via NLP
286    lemmatization.
287     The two scans produce one candidate stream. The generator records the matched span for each
288    remaining candidate, and derives a factual written value from the sentence, component name, and
289   approved aliases. The value is exact when the sentence writes the complete catalog name. It is
290   alias when the sentence writes an approved alias. It is part when the name-word scan finds a
291   name word in the same or a different grammatical form. Or it is qualified name when the name
292    occurs inside a code identifier, such as “storage” in storage.api for the component Storage. Such
293   an occurrence may denote a code path rather than the architectural component itself.

      3.3  Coreference Route322
323   The coreference route handles sentences that refer to a component without writing its name. Such
324   a sentence may use a pronoun or noun phrase whose antecedent appears in the surrounding
325    discourse. Because a lexical scan cannot determine what this expression denotes, coreference
326    candidate generator uses an LLM to propose the resolution.
327      For each proposal, coreference candidate generator records the target sentence, the referring
328    expression, the proposed component, the antecedent sentence, and the antecedent text. These
329    candidates then enter into the judge. First, to ensure the antecedent is reliable for the reference,
330    a pre-hook verifies that the cited antecedent sentence writes either the component’s exact name
331    or via alias. A candidate that fails this condition is rejected before coreference judge is called. For
332    each remaining candidate, coreference judge receives the referring expression, the cited antecedent,
333    the target sentence, and its preceding sentence. It accepts the candidate only when the referring
334    expression unambiguously denotes the proposed component and the target sentence makes an
335    architectural claim about that component.
336     The two cases in Figure 5 illustrate the coreference judgment. In Sentence 4, “It” refers to the
337   DB component introduced in local Sentence 3, and the target sentence states an architectural
338    responsibility of that component. The coreference judge therefore accepts the candidate. In the
339    rejected case, “This” in local Sentence 6 denotes the conversion operation described in local
340    Sentence 5 rather than unambiguously denoting Reencoding. The surrounding discourse concerns
341    reencoding, but that context alone does not establish the proposed component reference. The
342    coreference judge therefore rejects the candidate.

361   4 AN ARCHITECTURE-DRIVEN METRIC SUITE
362   Doc-code gold links are highly concentrated across components, so link-level averaged metrics
363   can hide whether a system covers every documented component. This section quantifies that
364    concentration across all five projects and builds a metric suite that exposes the components a
365   system leaves untraced.

366
367    4.1  Link Concentration in the Benchmark
368    Breaking down by components, document to code trace links have a highly unequal distribution.
369    Table 1 compares gold links per component at both task grains using the Gini coefficient (0 =
370    uniform, and larger values indicate greater concentration). Doc-code Gini ranges from 0.47 on
371    TeaStore to 0.59 on JabRef; doc-model ranges from 0.18 on TeaStore to 0.37 on BigBlueButton.
372   Doc-code has the higher per-component Gini in each of the five projects. To make this concrete: a
373    Gini of 0.59 means that if all trace links were income, the richest component would earn roughly
374   what the bottom 80% components earn combined. The median and maximum link counts also show
375    the concentration: on Teammates the median component has 861 trace links while the largest has
376    3,622; on JabRef the ratio is 768 to 3,888. Overall, the three largest components hold between 69.3%
377    (BigBlueButton) and 99.3% (JabRef) of the doc-code per-component link assignments. Link-level
378    metrics mainly reflect these few large components, hiding whether the system recovers the rest.
379   An architect’s primary job is not reading the benchmark average score. They read the architecture
380   document with models, and a hole in it is relevant regardless of the benchmark score. We therefore
381    define a suite that gives components explicit visibility and reports what the link-level average
382    buries.

383

446   5  EXPERIMENTAL EVALUATION
447  We study four research questions:
448
449    5.1  Research Questions
450   RQ1: Does ArchLinker recover trace links better than existing approaches?
451   Motivation: Existing approaches either match component names lexically [39] or recover com-
452    bining a single LLM call with similarity matching [30]. ArchLinker instead separates candidate
453    generation by reference form and uses an evidence-backed judge to check the generated candidates.
454  We evaluate whether this workflow improves recovery on both doc-model recovery task and the
455   downstream doc-code task.
456   RQ2: What component-level behavior do architecture-driven metrics tell beyond standard link-level
457
             metrics?
458
      Motivation: Link-level precision, recall, and 𝐹𝛽weight every link equally. We found that doc-code
459
       links are highly concentrated across components, so components with many links can dominate
460
      these aggregate scores. The link-level average is too coarse to show how recovery varies across
461
      components. We therefore examine whether proposed size-aware metrics reveal component-level
462
      misses which is difficult to see in the standard metrics.
463
464   RQ3: How much do the judges inside ArchLinker contribute to the final result?
465    Motivation: One key feature of ArchLinker is that each recovery route pairs candidate generation
466   with a corresponding evidence-backed judge. The judges can remove such false positives, but they
467   may also reject true links. We therefore measure which true and false links each judge rejects and
468   how disabling the judges changes the final precision-recall trade-off.
469   RQ4: What does each module of ArchLinker contribute on its own?
470   Motivation: ArchLinker recovers links through two reference forms: named mentions and coref-
471    erence mentions. The two recovery routes share the alias table constructed before candidate
472    generation. We examine whether the reference forms recover complementary links and measure
473   how recovery changes when the shared knowledge is unavailable.
474
475    5.2  Experiment Design
476   To answer the four research questions, we run four families of experiments on the ArDoCo bench-
477   mark, the largest benchmark to the best of our knowledge [28]. It contains five Java open-source
478    systems with hand-curated architecture docs, architecture models, and gold standard trace-links
479    at two grains, document-to-component and document-to-code. We use the released configura-
480    tions of the deterministic baselines. Because ArchLinker and Artemis are LLM-based therefore
481    non-deterministic, we run each three times and report the mean. The deterministic baselines are
482   run once. To avoid depending on one model, we run ArchLinker on two language-model backends,
483    GPT-5.6-terra and GPT-5.6-luna. Prompts, configurations, raw model responses, and experiment
484    outputs are included in the replication package [2].
485
486     5.2.1  Experiments for RQ1. We evaluate recovery at two grains.
487     (1) Doc-model. For every sentence in the architecture document, a system recovers links between
488       the architecture model components described by that sentence. We compare recovered links
489       with the doc-model gold standard. We compare ArchLinker with two baselines: SWATTR [39],

711     The no-knowledge variant disables alias discovery while retaining both linkers. The separately
712   run no-knowledge configuration is 7 pp lower in average F1 (0.94 →0.87) and 12 pp average F2
713    (0.95 →0.83) on doc-model, in these recorded run sets. The F2 penalty is disproportionately larger
714    because without the alias table, recall falls from 0.97 to 0.81 as components whose document names
715     differ from their model names lose all links; F2 weights recall four times as heavily as precision, so
716    this recall drop hits F2 harder than F1. The component-level differences are larger: worst-component
717    F1 falls from 0.76 to 0.44 (−32pp) and the harmonic per-component F1 from 0.91 to 0.52 (−39pp),
718    against −11pp of doc-code file F1, and the component miss rate rises from 0.0% to 10.8%. The effect
719     is concentrated rather than spread: the three components whose doc-code F1 falls to 0 without
720    the table, MediaStore’s DB and "Reencoding", and TeaStore’s ImageProvider, account for 47.5%,
721   1.7% and 45.3% of their project’s gold doc-code links, respectively. Therefore the modules are
722   complementary rather than interchangeable, and the knowledge module raises component-level
723    scores that the standard metric shows little of.
724
725      Answer to RQ4. named-reference route alone beats SWATTR; coreference route lifts average
726     F1 from 0.90 to 0.94 and average F2 from 0.89 to 0.95. The separate no-knowledge comparison
727      differs by 7pp average F1 and 12pp average F2 after rounding. The full configuration exceeds the
728    no-knowledge configuration by 32pp of worst-component F1.

736   7  DISCUSSION
737    7.1  Implications
738
         For researchers. Architectural traceability research should account for uneven link distributions
739
      across components, documents, artifact types, and other relevant groupings. As tracing extends
740
      across abstraction levels and into larger or more fine-grained artifact spaces, aggregate results can be
741
      dominated by densely represented regions and conceal failures in sparsely represented groups. Our
742
     framework supports studying this behavior by evaluating recovery at multiple scopes and inspecting
743
      candidate generation, contextual judgment, and downstream mapping separately. Researchers can
744
      therefore locate where performance changes as distributions become more uneven or the tracing
745
      scope broadens, and report results for relevant subsets alongside aggregate performance.
746
747      For practitioners. ArchLinker lets practitioners configure the precision–recall trade-offby en-
748    abling or disabling the judges. Disabling both judges raises recall by 3 pp but lowers precision by
749    24 pp (RQ3); practitioners whose cost of missing a link is high can run the unjudged variant and re-
750   view the extra candidates. On the five benchmark projects, the total inference cost is approximately
751    US$0.47 at current GPT-5.6-terra pricing, comparable to Artemis’s US$0.32 (Table 3).
752     The size-aware metrics require no extra annotation beyond the existing gold standard and can
753    serve as a diagnostic: they show which components a tool under-serves, directing human review
754   where it is most needed.
755
756    7.2  Remaining Weaknesses
757   ArchLinker does not solve the whole task. Its macro-averaged worst-component F1 on doc-code
758     is 0.76, and on BigBlueButton it falls to 0.44. BigBlueButton has the highest doc-model Gini
759    coefficient among the five projects (0.37, Table 1), meaning its doc-model links are the most
760    unevenly distributed; its 12 components and 87 documentation sentences make uniform coverage
761     difficult. On Teammates, the worst-component F1 is 0.72, well below the link-level F1 of 0.77.
762   The size-aware suite makes this headroom visible where the link-level average would suggest
763    near-saturation.
764     The MediaStore doc-code result illustrates a limitation of transitive trace link: ArchLinker
765    gains 2 pp of doc-model F1 over Artemis but loses 6 pp on doc-code F1. A doc-model advantage
766    concentrated on small components does not survive transitive composition when those components
767   expand into fewer code files.
768
769    7.3  Threats to Validity
770       Internal validity. The LLM systems are stochastic. So we report scores across three runs per project.
771    All five benchmark projects are public open-source systems whose source code and documentation
772    are available on GitHub. The LLM backend has very likely encountered them during pre-training. We
773    therefore re-ran baseline approach Artemis on the same LLM backend ArchLinker uses. Therefore,
774   two systems then share the same exposure and use the same model, so what separates them is
775    the workflow. Secondly, the improvement could come from the extra LLM calls rather than the
776   workflow itself. The ablations (RQ3, RQ4) rule this out by attributing it to specific modules, each
777    contributing a non-redundant slice of links. Alias discovery and coreference resolution may benefit
778      if the model has internalized project-specific vocabulary. A definitive memorization test would
779    require projects the model has not seen, which is difficult to guarantee for any public system.
780
781      External validity. We measure on the five Java systems of the ARDoCo benchmark, the largest
782    curated one we know of [28]. Results may not transfer to other languages, industrial systems, or
783    differently written documents. We mitigate this by using all five projects, which span two orders of

     8  RELATED WORK
794
795   ArchLinker sits at the intersection of four areas: traceability link recovery, NLP for requirements
796    engineering, LLM-based software engineering, and hallucination control in LLM workflows.
797       Traceability link recovery. Automated traceability link recovery grew out of the requirements-
798    traceability problem [32, 59], and it is still a long-standing open problem for the community [4].
799    Lago, Muccini, and van Vliet showed that traces can be maintained to the activities stakeholders
800   must carry out [40]. For two decades, the main family of trace link recovery methods scored each
801    artifact pair by textual similarity from information retrieval methods [9, 19]. Examples include
802    vector-space and probabilistic models [3], latent-semantic indexing [48], artifact-management
803    variants [18], and test-to-code recovery [57, 58]. On the practical side, previous work estimated
804   how many links are still missing [25], showed that the links pay off during maintenance [46],
805   and identified the factors behind successful traceability maintenance [49]. manage traceability
806    information models in practice [50]. Links embedded in commit messages also evolve and decay over
807    time [69]. The learning-based ones include fused textual and structural signals [52], hierarchical
808    Bayesian networks [53], multi-layered bug-to-fix recovery [55], and pre-trained BERT encoders [42].
809   On the architecture side, the documentation, model, and code must stay consistent [13, 15, 41],
810   and an architecture-centric lifecycle frames how requirements reach code [10]. Design-decision
811    rationale can be codified with tool support [12], and the community has examined how to sustain this
812   knowledge over time [14]. Architecture-based testing checks the code against the description [54].
813   The ARDoCo line sets the benchmark and the doc-model-code pipeline we compare against [38, 39].
814   Artemis extends it with LLM-based entity extraction: it builds an entity list from the document and
815   matches entities to the model by name and embedding similarity [30]. Although Artemis extracts
816    knowledge, its link decision is a similarity threshold, not a judgment against the sentence’s evidence.
817   So a plausible match that the sentence does not support still becomes a link. LiSSA classifies each
818    documentation-and-target pair with one LLM call augmented by retrieval [29]. The classification is
819    also unverified. ArchLinker differs from both by pairing each candidate generator with a judge that
820    receives the evidence the candidate rests on.
821
822      NLP4RE.. The recurring obstacle for trace-link recovery is the vocabulary gap: a single concept
823   can appear under many surface forms. The requirements-engineering community addresses this
824   with NLP techniques. Examples include glossary-term extraction [5], NLP-based change-impact
825    analysis over natural-language requirements [6], and practical guidelines for selecting NLP tech-
826    niques in requirements engineering [60]. Recent work applies LLMs to improve requirements
827    completeness [44, 45]. Mahmoud and Niu found that only focused semantic relationships help close
828    the vocabulary gap for IR-based tracing [47], and text-retrieval work rewrites queries to bridge
829    the same kind of mismatch [33]. Island parsing extracts structured fragments from the same noisy
830    artifacts [7]. Polysemy in identifier and requirement terms further hinders automated tracing [66],
831   and domain-specific corpora improve how ambiguity is handled [24]. AI-based question answering
832   has been applied to analyze natural-language requirements [23], and collaborative traceability

863   9 CONCLUSION
864   This paper presents ArchLinker, to our knowledge the first multi-stage LLM workflow for archi-
865    tecture document-to-model traceability link recovery that requires no task-specific fine-tuning.
866   ArchLinker derives an alias table once, then reuses it in two recovery routes—a named-reference
867    route for written names and name words, and a coreference route for implicit references. Each
868    route pairs a candidate generator with an evidence-backed judge that rejects links the evidence
869    does not support. The alias table is critical: without it, worst-component F1 falls by 32 pp and three
870   components lose all recovery. Alongside the approach we introduce an architecture-driven evalua-
871    tion suite that adds per-component measures to the standard link-level metric on doc-code, and
872    the component miss rate (CMR) on doc-model. On the ARDoCo benchmark, ArchLinker reaches a
873   doc-model average F1 of 0.936, 13 pp above the strongest baseline run on the same backend, and
874    carries this gain through to a doc-code average F1 of 0.879 (+7 pp). Under the size-aware suite
875    this lead widens to +30 pp worst-component F1 and +28 pp harmonic-mean per-component F1.
876    ArchLinker’s macro-averaged worst-component F1 is 0.76, well below its link-level F1, so the suite
877    also keeps this headroom visible where the standard metric alone would not.
