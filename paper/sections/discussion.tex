\section{Threats to Validity}
\label{sec:threats}

\paragraph{Internal validity.}
Three factors could bias our measurements.
First, the \ac{LLM} backend is non-deterministic.
We report every measured system as the mean of three runs---\approach{}, the re-run \Artemis{} baseline, and the RQ3/RQ4 ablations alike---and release every raw response~\cite{replication}.

Second, the backend may have seen the five public projects during pre-training, so memorization rather than the workflow could explain the gain.
We therefore re-ran \Artemis{} on GPT-5.6-terra, the backend \approach{} uses, and report that arm: the two systems then share the same exposure and the same model, so what separates them is the workflow.
We run it three times, as we run \approach{}, so neither system is credited with a lucky draw; its own runs differ enough to matter, abandoning a different component each time.
We keep \Artemis{} at its released GPT-5.4 configuration in the appendix, because the backend change is not neutral for it---it gains recall and loses precision, so its \fone\ falls while its \ftwo\ rises.
That released arm is a single recorded run, which is why it stays out of the body comparison.
Third, an implementation detail of the span test that excludes matches inside qualified identifiers treats a sentence-initial match as if it were inside one, so one span per sentence is suppressed.
We found this while auditing the deterministic layer and measured its repair over six paired runs: correcting it leaves recall unchanged and \emph{costs} $1.2$ false positives per run ($p=0.01$).
We therefore report it rather than silently keeping or silently fixing it.
A detail that a benchmark rewards is a detail fitted to that benchmark, whichever way it is resolved, and we expect the corrected behavior to be the one that transfers.

\paragraph{External validity.}
We measure on the five Java systems of the ARDoCo benchmark, the largest curated one we know of~\cite{fuchs_establishing_2023}; results may not transfer to other languages, industrial systems, or differently written documents.
We mitigate this by using all five projects, which span two orders of magnitude in size and several domains, and by keeping \approach{} training-free with no benchmark-specific tuning.
One choice is worth stating precisely under this heading: which form of the writing relation each linker scans (\autoref{tab:forms}) rests on a property of English---a capitalized token is a proper noun where the same token in lower case is often ordinary vocabulary---and we confirmed the resulting precision ordering on the benchmark rather than deriving it there.
The relation itself contains no project vocabulary, and its only word list is a closed set of English inflectional suffixes, so it carries nothing from these five documents to a sixth.
To show the gains do not depend on one model, we run \approach{} on two backends, GPT-5.6-terra and GPT-5.6-luna, and repeat the module ablation on both: the knowledge module is worth $7.6$pp \avgfone\ on the first and $3.3$pp on the second.

\paragraph{Construct validity.}
\ref{rq:metrics} assumes that recovering every documented component matters to developers; our size-aware metrics express this through worst-component and harmonic-mean per-component \fone{} on doc-code, and the \cmrname{} (\cmr) on doc-model, the share of gold sentence--component assignments whose component a system abandons.
These are proxies, so we keep the standard link-level \fone{} as the reference and report the size-aware view beside it.
They are also not a relabeling of \fone{}: a system can score well on \fone{} and still leave whole documented components untraced, which is exactly what the size-aware view exposes.
