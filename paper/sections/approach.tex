We propose \approach, a training-free \ac{LLM} workflow that recovers trace links between an architecture document and an architectural model.
Its input is a document $D$ with sentences $S = \{s_1, \ldots, s_n\}$ and a component set $C = \{c_1, \ldots, c_m\}$.
Its output is a link set $L \subseteq S \times C$.
Each link $(s_i, c_j) \in L$ asserts that sentence $s_i$ discusses the architectural responsibilities of component $c_j$.

Recovering these links has three challenges, and the workflow answers each with one design decision.

First, links are carried by various reference forms.
A sentence may state a component's exact name, as Sentence~11 of \autoref{fig:example} names \texttt{preferences};
or it may give only an alias the document coined, as Sentence~6 introduces \texttt{gui} as ``the UI'';
or it may carry only one word of a multi-word name, as a document naming an \texttt{HTML5 Client} later writes only ``each client'';
or it may lean on a pronoun, as Sentence~7 refers to \texttt{gui} by ``it''.
Prompting an \ac{LLM} therefore requires considering each of these forms, because one rule strict enough for the last is blind to the first.

Secondly, an \ac{LLM} can return a link that reads as plausible but has no support in the sentence,
so each link must be checked against its own evidence.

Thirdly, a project has a rich vocabulary about its components, which appear under aliases the document coins as it goes.
The underlying difficulty is the well-known vocabulary problem~\cite{furnas1987vocabulary}: people tend to use different terms to refer to the same object.

Handing the whole document to an \ac{LLM} does not settle this by itself, because the model can see the sentence that coins an alias and still fail to apply it where the alias is used.
The workflow must build this knowledge before it links, rather than leave each call to rediscover it.

\textbf{\approach in a nutshell.}
\approach answers the three challenges by three design decisions.
Targeting the challenge of various reference forms, \approach reaches them with two linker modules: the \linkerN and the \linkerC.
The \linkerN proposes by two lexical scans, the \linkerB for a sentence that writes a whole name of a component and the \linkerD for one that writes a single word of one; the \linkerC proposes by resolving a referring expression against the sentences around it.
Splitting the \emph{proposal} by form is what makes the forms reachable at all: a scan tight enough to be trusted on an exact name sees nothing in a sentence that writes no name, and a step loose enough to resolve a pronoun proposes far too much to be trusted on one.
%%%%%%%%%% C - Hallucination
To reduce hallucinated trace links, every proposed link is checked by an \ac{LLM} based judge.
Instead of merely guessing on the proposed link, we guide the judge with augmented context to reason about the architectural responsibility of the link: each proposer reports the text it actually matched and what the code can say about that match, as a structured \emph{evidence bundle}, and the judge is handed that bundle alongside the candidate, which is what makes each judge \evidenceBacked.
The judge therefore rules on what the proposer can show rather than on the link alone, which makes the verdict traceable to text in the document instead of to a second opinion.
Splitting the \emph{judging} does not follow from splitting the proposal, and \approach does not split it: both written forms are read by one \nameValidator under one rule, which states what a trace link is and how to read each field of the bundle.
What separates a sentence that writes a name from one that writes a single word of it is then a \emph{fact in the case} rather than a second standard applied to it, which is the division of labour \approach keeps throughout: the deterministic layer states facts about a case, and the \ac{LLM} weighs them.
%%%%%%%%%% C- Vocab
To address the vocabulary mismatch problem, \approach builds a reusable alias table.
Before linking, \approach scans the components and the document to build that table.
This is motivated by previous works on glossary mining for requirements~\cite{arora2017automated,gemkow2018automatic} and software synonym extraction~\cite{howard2013automatically,falleri2010automatic}.

Every scan and every judge reads that one table, so a name the project coined once is recognized wherever it is used and no linker has to rediscover it mid-run.

Together these decisions give the workflow of \approach in \autoref{fig:approach-overview}: the alias discovery module, two linkers reaching three reference forms, and \evidenceBacked judges.

\subsection{Alias Discovery}\label{sec:doc-understanding}
Stage~1 analyzes the document against the component set to find the aliases the developers coined.
This helps linkers match a document sentence to a component even when the sentence uses a term that is not the component's exact name.
\approach discovers these aliases from the document at runtime, and they come in two kinds.
The first is an explicit renaming, where the document itself ties a short form to a name: an abbreviation or a synonym.
The second is a shorthand, one word of a multi-word name used on its own after the document has introduced the name.

An \ac{LLM} judge confirms each proposed alias before it enters the alias table, rejecting a phrase that is generic vocabulary, names the whole system, names a different component, or names a group of elements rather than one.
A term that two components both claim is taken to name neither, and is dropped before any linker reads it.

\subsection{\linkerN}\label{sec:name-linker}

\linkerN consists of two lexical link proposers and one \ac{LLM} based judge.
Both proposers scan the document $S$ together with the alias table, spend no \ac{LLM} call, and return candidate links, $(s,c)$ pairs.
The \linkerB marks a sentence that writes a whole name of a component, under any capitalization and under any short form the alias table confirmed.
The \linkerD reaches a sentence that writes only part of one: it matches a sentence word against the words of a component's name under English inflection, so a document that names an \texttt{HTML5 Client} and later writes only ``each client'' is reached where the \linkerB sees nothing.
For example, in \autoref{fig:example} Sentence~11 writes the name of the \texttt{preferences} component, so the \linkerB proposes $(s_{11}, \texttt{preferences})$; Sentence~7 uses the same word as ordinary English while its topic is \texttt{gui}, and the proposer cannot tell the two apart, because what it knows is only that the characters are there.

The looser scan makes one refusal of its own.
When every writing of the matched word falls inside a span where the sentence writes another component's whole name, the sentence is naming that other component there, and the pair is that component's.
A sentence reading ``events are published on the \texttt{Redis PubSub} channel'' therefore yields no candidate for \texttt{Redis DB}, the sibling component whose name shares the word \texttt{Redis}.
The refusal reads the model catalog and not the alias table, and the asymmetry is deliberate: a scan only ever proposes, so it may rest on a sampled \ac{LLM} output, whereas this predicate is the one thing in the layer that \emph{ends} a case and so may rest only on what is given.

Both proposers feed one stream, and one judge reads it under one rule (\autoref{prompt:judge}).
The rule states what a trace link is and how to read each field of the evidence bundle, and it states no default and no per-form standard: whether the sentence wrote a whole name, a confirmed short form or a single word is a \emph{field of the case}, not a different question asked of it.
What the field changes is what the judge is weighing rather than how strictly it weighs: a shorter surface leaves more readings of the expression open, and the bundle names the other components the same word could reach, so the judge can see what this expression might be doing instead of naming this component.
The alternative set is the clearest instance of that division, because it is a fact no judge can be asked to recompute: which components the sentence's words could reach is settled by the catalog, while which reading the sentence actually has is settled only by reading it.

A case carries a component only where the match computed one.
The \linkerD reaches a sentence through a single word, and one word of a name identifies nothing, so such a case names the expression and not the component, and its call is asked what the expression denotes: a participant in the system, or something merely associated with software (\autoref{prompt:denote}).
This is the same rule with the reply contract its own evidence licenses, not a second rubric: shown a component to confirm, the \ac{LLM} tends to confirm identity rather than test it, so the case that has no identity to offer must not be given one.
Every verdict rests on a quote the judge commits to first, and a verdict carrying no quote does not count, since a judge that must point at text cannot approve on an impression.

\subsection{\linkerC}\label{sec:coref-linker}

\linkerC recovers the links in sentences that write no component name, where a component is mentioned only by coreference.
%CHECK [correction: no pronoun filter] (2026-09-07) The draft said 'For each sentence with
%  a pronoun like it'. s110's _resolve_references: 'Every sentence goes to the LLM in
%  context; no pronoun regex.' MANUAL CHECK: this contradicts any earlier text describing
%  a pronoun-triggered coreference stage.
Such links are component mentioned in S XXX sentence (antecedent sentence). 
A later sentence describe the component again refering by pronouns like "it / that". 
In such case, antecedent sentences are is not decided in advance.
Since this step requires semantic reasoning, we use an \ac{LLM} step to propose link candidate. 
It reads each sentence and its surrounding sentences, and  reports which pronoun pointing back, to which earlier sentence.
For illustration, suppose a later sentence reads ``It stores the user's settings,'' naming no component: \linkerC resolves ``It'' to an earlier sentence that named \texttt{preferences} and proposes the link to \texttt{preferences}, reporting that earlier sentence as its evidence.
The candidates are then judged by the \corefValidator{}, which is shown the referring expression and the antecedent the resolver committed to, and rules on whether that commitment holds.

\begin{promptL}{\linkerC: Coreference Resolution}{coref}\\
{\scriptsize\ttfamily\raggedright

noun phrase) to components.\\
COMPONENTS: \{comp\_names\}\\
SENTENCES: \{Sn: text\}\\
\{per case: TARGET Sn + NAMED BEFORE THIS\\
~~CASE: Name (Sm), ... nearest first\}\\
Quote the referring expression, then the\\
entries it could point to, then the one\\
it does.\\
Resolve when the surrounding sentences make\\
one component the clear antecedent, under any\\
form the document uses for it. Avoid\\
resolving when two or more equally plausible\\
antecedents exist.\\
Return JSON:\\
~~\{"resolutions": [\{case, sent, ref,\\
~~~~candidates, component, ant\_sent,\\
~~~~ant\_text\}]\}
}
\end{promptL}
