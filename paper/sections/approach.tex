We propose \approach, a training-free \ac{LLM} workflow that recovers trace links between an architecture document and an architectural model.
Its input is a document $D$ with sentences $S = \{s_1, \ldots, s_n\}$ and a component set $C = \{c_1, \ldots, c_m\}$.
Its output is a link set $L \subseteq S \times C$.
Each link $(s_i, c_j) \in L$ asserts that sentence $s_i$ discusses the architectural responsibilities of component $c_j$.

Recovering these links has three challenges, and the workflow answers each with one design decision.

First, links are carried by various reference forms.
A sentence may state a component's exact name, as Sentence~11 of \autoref{fig:example} names \texttt{preferences};
or it may give only an alias the document coined, as Sentence~6 introduces \texttt{gui} as ``the UI'';
or it may carry only one word of a multi-word name, as a document naming an \texttt{HTML5 Client} later writes only ``each client'';
or it may lean on a pronoun, as Sentence~7 refers to \texttt{gui} by ``it''.
Prompting an \ac{LLM} therefore requires considering each of these forms, because one rule strict enough for the last is blind to the first.

Secondly, an \ac{LLM} can return a link that reads as plausible but has no support in the sentence,
so each link must be checked against its own evidence.

Thirdly, a project has a rich vocabulary about its components, which appear under aliases the document coins as it goes.
The underlying difficulty is the well-known vocabulary problem~\cite{furnas1987vocabulary}: people tend to use different terms to refer to the same object.

Handing the whole document to an \ac{LLM} does not settle this by itself, because the model can see the sentence that coins an alias and still fail to apply it where the alias is used.
The workflow must build this knowledge before it links, rather than leave each call to rediscover it.

\textbf{\approach in a nutshell.}
\approach answers the three challenges by three design decisions.
Targeting the challenge of various reference forms, \approach has an architecture of three linker modules: the \linkerB, the \linkerD, and the \linkerC.
%CHECK [xx: benefit 1/3] (filled 2026-09-07) Was: 'They XXX, benefit.'
%  Filled with the N4 spine sentence. MANUAL CHECK: this is the section's load-bearing
%  claim; it should not also be asserted in intro.tex in the same words.
Splitting by form is what lets the checks differ: a judge can be no stricter than the evidence its own linker reports, so one linker per form buys one standard of proof per form.
%%%%%%%%%% C - Hallucination
To reduce hallucinated trace links, each proposed link is checked by an \ac{LLM} based judge.
Instead of merely guessing on the proposed link, we guide the judge with augmented context to reason about the architectural responsibility of the link: every linker reports the text it actually matched, as a structured \emph{evidence bundle}, and the judge is handed that bundle alongside the candidate, which is what makes each judge \evidenceBacked.
%CHECK [xx: benefit 2/3] (filled 2026-09-07) Was: 'Therefore, the judge xxx benefit.'
The judge therefore rules on what the linker can show rather than on the link alone, which makes the verdict traceable to text in the document instead of to a second opinion.
%%%%%%%%%% C- Vocab
To address the vocabulary mismatch problem, \approach builds a reusable alias table.
Before linking, \approach scans the components and the document to build that table.
This is motivated by previous works on glossary mining for requirements~\cite{arora2017automated,gemkow2018automatic} and software synonym extraction~\cite{howard2013automatically,falleri2010automatic}.

All three linkers read that one table, so a name the project coined once is recognized wherever it is used and no linker has to rediscover it mid-run.

Together these decisions give the workflow of \approach in \autoref{fig:approach-overview}: the alias discovery module, the architecture of three reference-form linkers, and \evidenceBacked judges.

\subsection{Alias Discovery}\label{sec:doc-understanding}
Stage~1 analyzes the document against the component set to find the aliases the developers coined.
This helps linkers match a document sentence to a component even when the sentence uses a term that is not the component's exact name.
\approach discovers these aliases from the document at runtime, and they come in two kinds.
The first is an explicit renaming, where the document itself ties a short form to a name: an abbreviation or a synonym.
The second is a shorthand, one word of a multi-word name used on its own after the document has introduced the name.

An \ac{LLM} judge confirms each proposed alias before it enters the alias table, rejecting a phrase that is generic vocabulary, names the whole system, names a different component, or names a group of elements rather than one.
A term that two components both claim is taken to name neither, and is dropped before any linker reads it.

\subsection{\linkerB}\label{sec:entity-linker}

\linkerB consists of a lexical link proposer and an \ac{LLM} based judge.
The proposer scans the document $S$ together with the alias table to mark the sentences that describe a component, returning a set of candidate links, $(s,c)$ pairs.
Because this linker targets the simplest reference form, the exact mention, a substring scan is enough and the proposer spends no \ac{LLM} call.
Each candidate is tagged with the matched sentence and the source (exact or by alias), forming the candidate's evidence bundle.
Candidates and their evidence bundles are the input for the link judge.
For example, in \autoref{fig:example} Sentence~11 names the \texttt{preferences} component, so \linkerB returns the candidate $(s_{11}, \texttt{preferences})$ with an evidence bundle recording the matched name ``preferences'' and the source ``exact name'' as the reason.
Sentence~7 uses the same word ``preferences'' while its topic is \texttt{gui}.
When the scanner proposes the false link $(s_{7}, \texttt{preferences})$, it is the judge's responsibility to reject it.
The judge rules once on the candidate and its bundle, weighing together whether the sentence makes an architectural claim about the component and whether the name identifies that component rather than serving as ordinary vocabulary (\autoref{prompt:judge}).

\begin{promptL}{\evidenceBacked Judge}{judge}\\
{\scriptsize\ttfamily\raggedright
Validate components in a document.\\
COMPONENTS: \{comp\_names\}\\
Approve the link by default: the component is\\
named here and the document treats it as part\\
of the system. A mention that says nothing\\
further about it still counts. Reject only on\\
a positive ground: the sentence asserts\\
nothing of this component, the name is doing\\
some other job here, or the sentence denies\\
what it would otherwise say of it.\\
An expression occurring only inside a longer\\
joined or dotted identifier names a piece of\\
that identifier, not a participant.\\
Some sentences use an ordinary English word\\
that coincides with a component's name.\\
Approve only when the sentence uses that word\\
as the name of the component. Capitalization\\
is evidence for a name and its absence\\
evidence against; neither settles it alone.\\
For each case, first quote the EXACT words\\
that state the architectural claim (or\\
"none"), then decide approve true/false.\\
CASES: \{cases\}\\
Return JSON:\\
~~\{"validations": [\{case, claim, approve\}]\}
}
\end{promptL}

\subsection{\linkerD}\label{sec:partial-linker}

\linkerD reaches the sentences that carry only part of a component's name.
It can be seen as a fuzzy matching between the document and the components: the proposer matches a sentence word against the words of a component's name under English inflection.
For example, a document that names an \texttt{HTML5 Client} may later write only ``each client'', missed by \linkerB.
\linkerD's proposer matches that link and records the matched word as its evidence.
The scan makes one refusal of its own: when every writing of the matched word falls inside a span where the sentence writes another component's whole name, the sentence is naming that other component there, and the pair is that component's.
A sentence reading ``events are published on the \texttt{Redis PubSub} channel'' therefore yields no candidate for \texttt{Redis DB}, the sibling component whose name shares the word \texttt{Redis}.
The refusal reads the model catalog and not the alias table, and the asymmetry is deliberate: a scan only ever proposes, so it may rest on a sampled \ac{LLM} output, whereas this predicate is the one thing in the layer that \emph{ends} a case and so may rest only on what is given.
After that, a judge decides whether the matched term denotes a software component or something merely mentioned.
The judge is shown the expression and its context but never the component, so it rules on what the expression denotes rather than on whether a proposed identity holds: shown the target, the \ac{LLM} tends to confirm identity rather than test it.

\subsection{\linkerC}\label{sec:coref-linker}

\linkerC recovers the links in sentences that write no component name, where a component is mentioned only by coreference.
%CHECK [correction: no pronoun filter] (2026-09-07) The draft said 'For each sentence with
%  a pronoun like it'. s110's _resolve_references: 'Every sentence goes to the LLM in
%  context; no pronoun regex.' MANUAL CHECK: this contradicts any earlier text describing
%  a pronoun-triggered coreference stage.
Which sentences those are is not decided in advance: an \ac{LLM} step reads every sentence in its context and reports the referring expression it finds, a pronoun or a noun phrase pointing back, with the earlier sentence and the component it resolves to.
A sentence carrying no such expression yields no resolution, so no rule has to guess in advance where one is.
This resolution is the one judgment only an \ac{LLM} can make, and it is where \linkerC does its real work.
For illustration, suppose a later sentence reads ``It stores the user's settings,'' naming no component: \linkerC resolves ``It'' to an earlier sentence that named \texttt{preferences} and proposes the link to \texttt{preferences}, reporting that earlier sentence as its evidence.
The resolver is not left to find the antecedent in the catalog at large: each case carries, computed in code, the components the sentences above it actually name, each with the sentence that names it, nearest first.
The division is between what is a fact and what is a weighing: which components the earlier sentences name is settled exactly, while which reading a referring expression carries in its sentence is in no table.
That list is a prior and not a constraint: the resolver may answer outside it, and what the code checks is the answer's sentence numbers, not its membership in the list.
The candidates are then judged by the \corefValidator{}, which is shown the referring expression and the antecedent the resolver committed to, and rules on whether that commitment holds.

\begin{promptL}{\linkerC: Coreference Resolution}{coref}\\
{\scriptsize\ttfamily\raggedright
Resolve refer-back references (pronoun or\\
noun phrase) to components.\\
COMPONENTS: \{comp\_names\}\\
SENTENCES: \{Sn: text\}\\
\{per case: TARGET Sn + NAMED BEFORE THIS\\
~~CASE: Name (Sm), ... nearest first\}\\
Quote the referring expression, then the\\
entries it could point to, then the one\\
it does.\\
Resolve when the surrounding sentences make\\
one component the clear antecedent, under any\\
form the document uses for it. Avoid\\
resolving when two or more equally plausible\\
antecedents exist.\\
Return JSON:\\
~~\{"resolutions": [\{case, sent, ref,\\
~~~~candidates, component, ant\_sent,\\
~~~~ant\_text\}]\}
}
\end{promptL}
