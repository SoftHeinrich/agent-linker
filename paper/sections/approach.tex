We propose \approach, a training-free \ac{LLM} workflow that recovers trace links between an architecture document and an architectural model.
Its input is a document $D$ with sentences $S = \{s_1, \ldots, s_n\}$ and a component set $C = \{c_1, \ldots, c_m\}$.
Its output is a link set $L \subseteq S \times C$.
Each link $(s_i, c_j) \in L$ asserts that sentence $s_i$ discusses the architectural responsibilities of component $c_j$.

Recovering these links has three challenges, and the workflow answers each with one design decision.
First, the project's vocabulary is not given in advance: a component appears under aliases the document coins as it goes, and some component names are ordinary English words that can't be simply matched. The workflow must build this knowledge before it links.
Second, links are carried by different reference forms. 
A named reference puts a component's name or an alias in the sentence; 
an implicit reference names nothing and leans on a pronoun resolved to an earlier sentence. 
One linker cannot serve both well.
Third, an \ac{LLM} can return a link that reads as plausible but has no support in the sentence, 
so each link must be checked against its own evidence.

\textbf{\approach in a nutshell.}
\approach answers the three challenges in three steps (\autoref{fig:approach-overview}).
It first builds a runtime \emph{knowledge module}, an alias table and an ambiguity map computed once from the components and the document.
It then runs two linkers, one for named references and one for implicit ones, enhanced by the knowledge.
Each proposed link is checked by an \evidenceBacked judge, and the surviving links are merged into the output.
By recovering the implicit references other tools silently drop, \approach{} aims to leave no documented component abandoned---the silent component failure that the doc-model silent-failure mass (SFM) of \autoref{sec:metric} measures.

\subsection{Design of \approach}\label{sec:arch}

Three decisions fix the shape of the workflow.

The first decision answers the project-knowledge challenge: the workflow gathers what it needs to know about a project once, up front, rather than leaving each linker to work it out on its own.
The underlying difficulty is the vocabulary problem~\cite{furnas1987vocabulary}: one component can appear under many names, and some of those names are ordinary English, so plain lexical matching is unreliable.
\approach builds this knowledge before linking, as a separate stage, in the spirit of glossary mining for requirements~\cite{arora2017automated,gemkow2018automatic} and software-side synonym networks~\cite{howard2013automatically,falleri2010automatic}.

The second decision answers the reference-form challenge: how to split the linking work.
A trace link $(s,c)$ between a sentence $s$ and a component $c$ takes one of two families.
In the \emph{named family}, a sentence in $s$ matches the exact name $\mathrm{name}(c)$ or one of the project-specific aliases $A(c)$ found for $c$: its abbreviations and synonyms.
In the \emph{implicit family}, $s$ carries no such direct mention, but a pronoun in $s$ resolves to an earlier sentence that does; we call this the \emph{structural antecedent constraint}.
The two families ask different questions, whether a text names a component, or whether a pronoun points to a sentence that names one, so they need different evidence and different judges.
The workflow therefore uses two linkers, one per family (\linkerB for the named family, \linkerC for the implicit family), rather than one large \ac{LLM} call that previous works used.

The third decision answers the reliability challenge: how to handle the non-determinism of the \ac{LLM}.
An \ac{LLM} linker can return a wrong link that still reads as plausible, with nothing in the sentence to support it.
\approach therefore makes each linker report the text evidence it used in a structured \emph{evidence bundle} and 
has each judge check the candidate link against that. 
A hallucinated link is caught by a mismatch between bundle and sentence.

\subsection{Project Knowledge Discovery}\label{sec:knowledge}
Stage~1 runs two modules in parallel: a \emph{model-understanding module} analyzes the component set to find ambiguous components that can be seen as ordinary-English words,
and a \emph{document-understanding module} analyzes the document to find aliases.

\subsubsection{Architectural Model Understanding}\label{sec:model-understanding}

Most component names, multi-word names, CamelCase compounds, and acronyms, are clear architectural identifiers.
The hard case is the single common-English word: in JabRef (\autoref{fig:example}) the component \texttt{preferences} shares its name with the everyday word ``preferences,'' so matching on it directly links sentences that merely use the word, producing false positives.
\approach builds the \emph{ambiguity map} with a hybrid rule: prompting an \ac{LLM} on the suspicious cases, i.e., lowercase words.

\begin{promptL}{Ambiguity Classification (Model Understanding)}{ambiguity}\\
{\scriptsize\ttfamily\raggedright
Classify these component names.\\
NAMES: \{comp\_names\}\\
\{AMBIGUITY\_RULE\}\\
Return JSON:\\
~~\{"architectural": [...], "ambiguous": [...]\}
}
\end{promptL}

\subsubsection{Architectural Document Understanding}\label{sec:doc-understanding}
An alias lets a linker match a document phrase to a component even when the phrase is not the component's exact name.

\approach discovers these aliases from the document at runtime, and they come in two kinds.
The first is an explicit renaming, where the document itself ties a short form to a name: an abbreviation in a parenthetical definition, or a synonym in a clear restatement.
The second is a partial reference, a bare \emph{trailing word}: the last word of a multi-word component name used on its own.
Trailing-word shorthands are common, but many trailing words are also generic English whose meaning depends on context, so this is the hard kind.
\approach extracts both kinds, and for each risky trailing-word candidate it checks the word against the ambiguity map and has an \ac{LLM} judge confirm the mapping before it enters the alias table.
This is where the two modules meet: without the ambiguity map, generic English would leak into the alias table through the trailing-word kind.

\begin{promptL}{Alias Extraction (Document Understanding)}{alias}\\
{\scriptsize\ttfamily\raggedright
Find alternative names used for the components.\\
COMPONENTS: \{comp\_names\}\\
\{EXTRACTION\_RULE\}\\
\{SCOPE\_RULE\}\\
DOCUMENT: \{doc\_lines\}\\
Return JSON:\\
~~\{"aliases": [\{term, component, scope\}]\}
}
\end{promptL}

\subsection{\linkerB}\label{sec:entity-linker}

% Without the knowledge module, a named-mention linker would handle the all named mention forms from scratch.
% The alias table removes this need: once it exists, every named form is just a sentence in $s$ that matches the exact name or one of the recorded aliases, so a single extraction step covers them all.
\linkerB reads each sentence together with the two tables and asks the \ac{LLM} to mark the sentences that describe a component, 
returning a candidate link $(s,c)$.
Each candidate is tagged with the matched sentence, the reference form, and a short reason, forming the candidate's evidence bundle.
Candidates and their evidence bundles will be the input for the link judge.
For example, in \autoref{fig:example} Sentence~11 names the \texttt{preferences} component, so \linkerB returns the candidate $(s_{11}, \texttt{preferences})$ with an evidence bundle recording the matched name ``preferences'' and the reference form as the reason.
Sentence~7 uses the same word ``preferences'' while its topic is \texttt{gui}.
Although we prompt the \ac{LLM} to propose a link only when the topic is the matched component, the \ac{LLM} may not follow the rule or may be unable to understand architectural roles.
If \linkerB also proposes the false link $(s_{7}, \texttt{preferences})$, it will be the judge's responsibility to reject it.

\begin{promptL}{\linkerB: Named-Reference Extraction}{entity}\\
{\scriptsize\ttfamily\raggedright
Extract ALL references to components.\\
COMPONENTS: \{comp\_names\}\\
KNOWN ALIASES: \{aliases\}\\
\{EXTRACTION\_RULE\}\\
DOCUMENT: \{Sn: text\}\\
Return JSON:\\
~~\{"references": [\{sentence, component,\\
~~~~matched\_text\}]\}
}
\end{promptL}

\subsection{\linkerC}\label{sec:coref-linker}

\linkerC recovers the implicit references that carry no explicit mention of any component.
For each sentence with a pronoun like 'it',  an \ac{LLM} step resolves the pronoun to an earlier sentence and a candidate component as evidence.
This resolution is the one judgment only an \ac{LLM} can make, and it is where \linkerC does its real work.
For illustration, suppose a later sentence reads ``It stores the user's settings,'' naming no component: \linkerC resolves ``It'' to an earlier sentence that named \texttt{preferences} and proposes the implicit link to \texttt{preferences}, reporting that earlier sentence as its evidence.

\begin{promptL}{\linkerC: Implicit-Reference Resolution}{coref}\\
{\scriptsize\ttfamily\raggedright
Resolve refer-back references (pronoun or\\

\{per case: CONTEXT lines + TARGET Sn (marked)\}\\
\{COREF\_RULE\}\\
\{ANTECEDENT\_RULE\}\\
Return JSON:\\
~~\{"resolutions": [\{case, sent, ref,\\
~~~~component, ant\_sent, ant\_text,\\
~~~~via\_alias\}]\}
}
\end{promptL}

\subsection{Evidence-Backed Judges}\label{sec:validators}

\acp{LLM} bring rich semantic understanding but are non-deterministic and can hallucinate.
Left unchecked, this would bring false positive links.
Two observations shape the judge design.

First, a judge should rule on a candidate from its evidence, not guess at it again.
Instead of re-classifying the link from scratch, each judge checks the candidate against the evidence bundle the linker reported.
This keeps the judge and the linker working from the same text.
Where a plain \ac{LLM}-as-a-judge sees only the candidate link, we augment the judge's input with that evidence bundle---the matched span, the reference form, and, for an implicit reference, the antecedent sentence---which is what makes each judge \emph{context-augmented}.

Second, the two linkers pose different questions, so their judges do different work.
A named mention has to clear two bars: the sentence must be \emph{relevant}, an architectural action that belongs to the component, and it must be \emph{unique}, pointing to that component rather than another or to a generic use of the word.
An implicit reference is simpler, because the alias lookup in \linkerC has already dropped every candidate whose earlier sentence does not name the component, so one question remains: whether the resolution fits the content of that earlier sentence.

The \entValidator{} therefore runs two passes, a relevance pass $p_1$ and a uniqueness pass $p_2$, and accepts a candidate only when both hold ($p_1 \land p_2$), since a trace link needs both.
The \corefValidator{} runs a single pass on its one remaining question, since the alias lookup has already done what a second pass would repeat.
We call this design \emph{\evidenceBacked judging}: each judge rules on a candidate from the evidence bundle the linker reported, with the number of passes matched to how hard the decision is. We treat it as a method contribution.

\begin{promptL}{Evidence-Backed Judge}{judge}\\
{\scriptsize\ttfamily\raggedright
Validate components. \{FOCUS\}\\
COMPONENTS: \{comp\_names\}\\
\{VALIDATION\_RULE\}\\
CASES: \{cases\}\\
Return JSON:\\
~~\{"validations": [\{case,\\
~~~~claim: "quote|none", approve\}]\}
}
\end{promptL}

\noindent All judges share this prompt; \texttt{\{FOCUS\}} and \texttt{\{VALIDATION\_RULE\}} are instantiated three times: the \linkerB relevance pass $p_1$ and uniqueness pass $p_2$, and the \linkerC single implicit-fit pass.
The checked links are then output as final recovered links.
