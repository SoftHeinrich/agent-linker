\section{Approach}\label{sec:approach}

\subsection{Overview}\label{sec:overview}

We propose an LLM-driven pipeline for recovering trace links between
Software Architecture Documents (SAD) and Software Architecture Models
(SAM).
Given a natural-language architecture document with sentences
$S = \{s_1, \ldots, s_n\}$ and a component model with components
$C = \{c_1, \ldots, c_m\}$, our approach produces a set of trace links
$L \subseteq S \times C$, where each link $(s_i, c_j)$ asserts that
sentence~$s_i$ discusses component~$c_j$.

\paragraph{Challenges.}
Five challenges make this task difficult for both lexical matchers
and standalone LLM classifiers:

\begin{description}
    \item[C1 --- Reference diversity.]
      Documents refer to components by canonical name, abbreviation,
      functional description, trailing word of a compound name,
      or pronoun.
      No single extraction strategy handles all types.
    \item[C2 --- Name ambiguity.]
      Component names are often common English words (\texttt{Core},
      \texttt{Adapter}) or technologies (\texttt{Redis}).
      These words appear frequently without referring to any component,
      and broadening extraction to capture diverse references increases
      false positives from such ambiguous names.
    \item[C3 --- Knowledge gap.]
      Alias tables, ambiguity classifications, and subprocess
      terms do not exist in advance; the system must discover
      this knowledge from raw inputs using the same LLM that will
      consume it---and the LLM may hallucinate aliases or misjudge
      ambiguity.
    \item[C4 --- LLM non-determinism.]
      LLMs produce different outputs across independent invocations of
      the same prompt.
      A single-pass design turns this variance into inconsistent
      link sets: false candidates that appear in one run but not
      another persist as false positives.
    \item[C5 --- Noise accumulation.]
      Combining multiple recovery strategies with different precision
      characteristics risks adding noise: each strategy may
      independently produce false positives that the others cannot
      detect.
\end{description}

\noindent Existing approaches address only part of this problem.
Lexical NLP pipelines such as SWATTR~\cite{TODO:swattr} rely on
string similarity and cannot resolve indirect references~(C1),
discourse dependencies~(C1), or false matches on generic
words~(C2).
LLM-based classifiers such as LISSA~\cite{TODO:lissa} add
semantic understanding but lack structured knowledge~(C3),
treat each sentence in isolation~(C1), and have no mechanism
to reduce their own non-determinism~(C4).

\paragraph{Key insight.}
Reliable recovery requires combining LLM reasoning with
structured architectural knowledge acquired before linking begins.
Different reference types need different resolution strategies,
but these strategies can operate independently on a shared
knowledge base; and a convention-aware boundary filter (hereafter
\emph{boundary filter}), based on architectural naming conventions,
catches false positives that neither lexical matching nor standalone
LLM classification can detect.
This decomposes the problem into three layers:
first resolving the \emph{knowledge gap}~(C3) before any linking
begins~(\S\ref{sec:knowledge});
then recovering links with \emph{type-specific strategies}~(C1)
that use this knowledge~(\S\ref{sec:recovery}); and finally
merging candidates and \emph{filtering remaining noise}~(C2,
C5) with the acquired knowledge~(\S\ref{sec:merge}).

\paragraph{Design patterns.}
Two cross-cutting patterns address C4 (LLM non-determinism)
throughout the pipeline:

\begin{itemize}
    \item \emph{Multi-pass consensus:}
      Decisions where precision matters use two independent LLM
      passes with task-specific agreement rules.
      The variant depends on the required confidence level:
      \emph{asymmetric voting} accepts high-confidence matches from
      either pass but requires agreement for uncertain ones
      (\S\ref{sec:seed});
      \emph{same-prompt intersection} runs an identical prompt twice
      and keeps only shared results (\S\ref{sec:entity});
      \emph{cross-validation debate} has one pass propose and another
      validate (\S\ref{sec:exclusion}).
    \item \emph{Citation-grounded verification:}
      Instead of trusting unverifiable LLM judgments, we require the
      LLM to produce checkable evidence---antecedent sentence
      citations, exact substrings---that code can verify
      deterministically.
      This makes hallucinated claims detectable (\S\ref{sec:coref},
      \S\ref{sec:evidence-filter}).
\end{itemize}

\noindent Additionally, all few-shot examples use abstract
placeholders or safe textbook domains; no benchmark names or
gold-standard information appears in any prompt.

\paragraph{Architecture.}
The pipeline is organized as a staged DAG
(Figure~\ref{fig:pipeline}) with three layers:

\begin{enumerate}
    \item \textbf{Knowledge acquisition} (Layer~1): Extracts
      component name properties, an alias table, and subprocess
      terms from raw inputs.
      Within this layer, independent analyses run in parallel
      sub-tiers where data dependencies allow
      (Figure~\ref{fig:pipeline}).
    \item \textbf{Link recovery} (Layer~2): Four complementary
      strategies produce candidate links, each targeting a distinct
      reference type (Table~\ref{tab:strategies}).
    \item \textbf{Link consolidation} (Layer~3): Merges all
      candidates, applies boundary filtering to
      \emph{all} links regardless of their source, and removes
      ungrounded references with a deterministic evidence filter.
\end{enumerate}

\subsection{Knowledge Acquisition}\label{sec:knowledge}

Before linking can begin, the pipeline must build structured
knowledge that later stages use.
Layer~1 addresses three knowledge gaps---name ambiguity
(\S\ref{sec:names}), alternative names (\S\ref{sec:alias}), and
subprocess identification (\S\ref{sec:exclusion})---through
targeted analyses whose dependencies are shown in the DAG
(Figure~\ref{fig:pipeline}).

\subsubsection{Name Ambiguity Classification}\label{sec:names}

\emph{Challenge~(C2):}
Component names vary widely in how specific they are.
Multi-word identifiers like \texttt{TaskScheduler} clearly
name architectural roles, but single common English words like
\texttt{Core} or \texttt{Adapter} often appear in text without
referring to any component.
The pipeline must know \emph{which} names need special care
before it encounters them in the document.

\emph{Insight:}
Structural cues (CamelCase, multi-word, all-uppercase) resolve
most ambiguity deterministically; LLM judgment is needed only for
the minority of names where structural cues are absent.

\emph{Design:}
Each name is classified as \emph{architectural} or
\emph{ambiguous} via a hybrid of deterministic structural guards
and LLM classification for structurally ambiguous names.
The classification feeds downstream decisions:
which candidates require generic-mention detection
(\S\ref{sec:entity}),
which trailing words need capitalized matching
(\S\ref{sec:alias}),
and which names receive stricter scrutiny in the boundary filter
(\S\ref{sec:boundary}).

Name analysis also detects \emph{implementation relationships}
(e.g., \texttt{BasicScheduler}~$\to$~\texttt{Scheduler}) by
shared-substring matching.
Implementation variants are excluded from later LLM prompts
and deduplicated by a parent-overlap guard at merge
time~(\S\ref{sec:dedup}).

\subsubsection{Alternative Name Discovery}\label{sec:alias}
%% Figure label: "Document Analysis (core)"

\emph{Challenge~(C1, C3):}
Documents refer to components by abbreviation (\emph{AST} for
\texttt{AbstractSyntaxTree}), trailing word (\emph{Dispatcher}
for \texttt{EventDispatcher}), or synonym.
Without an \emph{alias table} mapping these to canonical names,
any matching strategy will systematically miss such references,
limiting recall.
But building the table is itself error-prone~(C3): the LLM may
hallucinate mappings or accept generic words as aliases.

\emph{Insight:}
Different alias types require different validation rules.
Abbreviations and synonyms are validated structurally
(CamelCase $\to$ auto-approve) or semantically (judge prompt
with calibrated few-shot examples).
Partial references are the hardest case: whether a partial name
refers to a component depends on the surrounding context, and
requires frequency-based evidence followed by per-partial LLM
classification.

\emph{Design:}

\paragraph{Core discovery.}
An LLM extracts three alias categories: abbreviations
(parenthetical definitions), synonyms (unambiguous alternative
names), and partial references (trailing words of multi-word names
used alone).
A calibrated few-shot judge validates each mapping, rejecting
generic terms (\emph{system}, \emph{process}) while auto-approving
structurally unambiguous identifiers.
The resulting alias table is consumed by contextual discovery
(\S\ref{sec:entity}), abbreviated matching (\S\ref{sec:partial}),
and the boundary filter (\S\ref{sec:boundary}).

\paragraph{Partial-reference refinement.}
A frequency-based enrichment step adds partial mappings when a trailing
word appears in $\ge3$~sentences where the full name is absent and
no other component shares that word;
ambiguous trailing words require capitalized occurrences.
A subsequent per-partial LLM classification determines whether each
generic partial is used as a component reference (\textsc{name})
or as an ordinary English word (\textsc{ordinary}).
\textsc{Ordinary}-classified partials remain in the alias table
for deterministic matching (\S\ref{sec:partial}) but are
excluded from the alias context supplied to the boundary
filter (\S\ref{sec:boundary}), preventing it from treating
generic uses as validated component references.

\subsubsection{Subprocess Term Detection}\label{sec:exclusion}
%% Figure label: "Subprocess Term Learn."

\emph{Challenge~(C2, C3):}
Architecture documents describe not only components but also
their internal parts---terms like ``garbage collector'' inside
\texttt{MemoryManager}.
If left unrecognized, these create false positives in anaphoric
resolution, where a sentence about an internal mechanism is
misattributed to the enclosing component.

\emph{Insight:}
A single LLM pass produces too many subprocess terms because
some real component references look similar to internal-part
names.
A cross-validation debate---one pass proposes, another
validates---reduces this over-generation~(C4).

\emph{Design:}
Two independent LLM passes identify subprocess terms: the first
proposes candidates, the second validates them, rejecting terms
that may be valid component references.
Only terms confirmed by both passes are retained.
Subprocess terms are used as a strict filter in anaphoric
resolution (\S\ref{sec:coref}) and as context in validation
prompts (\S\ref{sec:entity}).

\subsection{Link Recovery}\label{sec:recovery}

With ambiguity classifications, the alias table, and subprocess terms
in hand, the pipeline proceeds to recover candidate trace links.

\emph{Challenge~(C1):}
No single strategy handles all reference types: canonical names
can be matched lexically, aliases require knowledge, pronouns
need discourse context, and abbreviated names require
project-specific awareness.

\emph{Insight:}
Type-specific strategies can run independently on the shared
knowledge base from Layer~1, each using the C4 mitigation
pattern that best fits its confidence level
(Table~\ref{tab:strategies}).
Their outputs are combined only at the Layer~3 merge point.

\subsubsection{Explicit Reference Extraction}\label{sec:seed}

\emph{Challenge~(C2, C4):}
Even canonical-name matching risks false positives from ambiguous
names and hierarchical namespace paths.
A single LLM pass produces inconsistent results across
runs---accepting a borderline candidate in one invocation and
rejecting it in the next.

\emph{Insight:}
Exact-name matches are high-confidence and reliably identified by
a single pass; non-exact matches risk hallucination and benefit
from independent agreement.
This difference motivates \emph{asymmetric voting} rather than
uniform intersection (which would lose reliable matches) or
uniform union (which would keep hallucinations).

\emph{Design:}
A self-contained extractor (which we call \textbf{ILinker2}) uses two
complementary LLM passes over batched document segments:
Pass~A (mention-framed) asks which components are explicitly
mentioned; Pass~B (actor-framed) asks which component is the
primary actor.
Both passes reject names inside hierarchical namespace paths and
generic English words.
Exact-name matches from \emph{either} pass are accepted (union);
non-exact matches require agreement from \emph{both}
(intersection).
Because ILinker2 requires no Layer~1 knowledge, it runs
in parallel with knowledge acquisition.

\subsubsection{Contextual Reference Discovery}\label{sec:entity}

\emph{Challenge~(C1, C4):}
Alias-based and functional references require knowledge that the
explicit extractor lacks, but broadening the extraction scope
also increases the risk of hallucinated links.

\emph{Insight:}
Running the \emph{same} broad-scope prompt twice independently
and keeping only shared results filters out hallucinations while
preserving the recall benefit of broader scope.
Using two different prompts would introduce prompt-specific
biases; using the same prompt ensures that disagreements between
the two runs come only from LLM non-determinism, which is
exactly what we want to filter.

\emph{Design:}
Knowledge-enriched prompts receive all known aliases from the
alias table, enabling recognition of abbreviations, synonyms, and
partial names that the knowledge-free extractor cannot match.
The extraction scope includes space-separated compound forms,
functional descriptions by name or role, interaction participants
(``X sends data to Y'' covers both X and Y),
passive and prepositional mentions (``handled by X'', ``via X'',
``through X''), and known alias occurrences.
The same prompt runs twice independently, and only candidates
found in both passes are kept.

For components that receive no links from either extraction or
discovery, a \emph{targeted recovery} step issues single-component
prompts with all known aliases, focusing LLM attention on
potentially overlooked references.

\paragraph{Validation.}
Candidates undergo multi-step validation:
\begin{enumerate}
    \item \emph{Generic-mention detection:}
      For components classified as ambiguous (\S\ref{sec:names}),
      an LLM determines whether each lowercase occurrence is a
      component reference or ordinary English usage,
      given the surrounding sentence context.
    \item \emph{Code-first auto-approval:}
      Candidates where the component name or a known alias appears
      verbatim in the sentence text (\emph{anchor sentence}) are
      accepted without further LLM review.
    \item \emph{Two-pass intersection:}
      Remaining candidates are validated by two independent LLM
      passes with complementary foci---\textsc{actor-role}
      (is the component the subject?) and \textsc{direct-reference}
      (does the sentence reference the component at all?).
      Only candidates approved by \emph{both} passes are retained.
\end{enumerate}

\subsubsection{Anaphoric Reference Resolution}\label{sec:coref}

\emph{Challenge~(C1, C4):}
Sentences containing pronouns (\emph{it}, \emph{they}, \emph{this},
\emph{these}, \emph{that}, \emph{those}) or definite descriptions
(\emph{the service}, \emph{this module})
carry valid trace information but contain no component name, so
the preceding strategies cannot find them.
However, LLMs can fabricate antecedents---claiming a pronoun refers
to a component in a sentence that does not actually mention that
component.

\emph{Insight:}
If the LLM is required to cite a specific antecedent sentence
with an exact quote containing the component name, hallucinated
resolutions become detectable by deterministic string
matching---so each resolution is either verifiably correct or
clearly fabricated.
A separate validation LLM call would itself be subject to
hallucination; deterministic verification eliminates this risk
entirely, given a correct citation.

\emph{Design:}
Each pronoun-bearing sentence is presented as an individual case
with a $\pm5$-sentence bidirectional context window, processed in
batches of~10.
The LLM must cite an antecedent sentence with the exact quote
containing the component name.
The code verifies this citation deterministically: the name (or
alias) must appear verbatim in the cited sentence, the antecedent
must be within 3~sentences (stricter than the context window to
prevent long-distance errors), and sentences about subprocess
terms (\S\ref{sec:exclusion}) are excluded.
Because the verification is strict and deterministic, anaphoric
links that pass all checks are accepted without further LLM review.

\subsubsection{Abbreviated Reference Matching}\label{sec:partial}

\emph{Challenge~(C1):}
Contextual discovery may miss sentences where a partial name
appears without other clues in the surrounding text.
Deciding whether ``Server'' refers to the component or is used
as a generic word requires project-specific context that a single
LLM prompt cannot reliably capture.

\emph{Insight:}
Deterministic matching gives stable recall at zero LLM cost;
the boundary filter in Layer~3 handles precision, since it
has the architectural context to tell generic uses apart from
component references.

\emph{Design:}
The pipeline deterministically scans all sentences for
word-boundary matches of each partial reference from the alias
table, producing links for uncovered pairs.
A clean-mention filter ensures the partial name appears as a
standalone word---not inside a dotted path, hyphenated compound,
or qualified name.
This strategy uses no LLM calls;
its output is evaluated individually by the boundary filter
(\S\ref{sec:boundary}).

\subsection{Link Consolidation}\label{sec:merge}

The four recovery strategies have now produced independent candidate
sets with different precision profiles.

\emph{Challenge~(C5):}
Independent strategies with different precision characteristics
produce three categories of noise:
overlapping candidates where multiple strategies found the same
link,
component names used in non-architectural senses that neither
lexical matchers nor standalone LLM classifiers can detect,
and hallucinated references that lack textual grounding.

\emph{Insight:}
Each noise category has a distinct structure that allows a
targeted fix: overlaps are resolved by source priority;
non-architectural name uses follow naming convention patterns
that an LLM can recognize with a structured reasoning guide;
and hallucinations lack textual grounding, so deterministic
string matching can detect them.

\subsubsection{Priority-Based Merge}\label{sec:dedup}

\emph{Challenge~(C5):}
Because recovery strategies operate independently, they may
discover the same $(s_i, c_j)$ pair via different evidence.
Without deduplication, the same link would carry multiple source
labels, which complicates later filtering.

\emph{Design:}
Overlaps are deduplicated, retaining the highest-priority source:
$\text{explicit} > \text{contextual} > \text{anaphoric} >
\text{abbreviated}$,
reflecting decreasing levels of direct textual evidence.
A \emph{parent-overlap guard} removes links to implementation
components when the abstract parent is already linked to the same
sentence, using the implementation relationships from name
analysis~(\S\ref{sec:names}).

\subsubsection{Convention-Aware Boundary Filter}\label{sec:boundary}

\emph{Challenge~(C2, C5):}
Even after merging, name ambiguity remains: some links survive
where a component name appears in a sentence but is used in a
non-architectural sense.
Simple regex-based checks catch some of these cases but miss
patterns that require reasoning about architectural naming
conventions.

\emph{Insight:}
Architectural naming conventions form a reasoning guide that an LLM
can apply reliably when constrained by structural guardrails.
For example, dotted paths imply namespace references rather than
component references, while components named after technologies make
every mention of that technology architecturally relevant.

\emph{Design:}
The boundary filter applies a structured reasoning guide to \emph{all}
links, regardless of which strategy produced them, checking two
rejection patterns:
\begin{enumerate}
    \item \emph{Hierarchical name reference:}
      The component name appears only as a prefix in a dotted or
      qualified path (e.g., ``\texttt{X.utils} provides helper
      functions'' does not reference component~X).
      An exception preserves links when the sentence also names the
      component explicitly.
    \item \emph{Name confusion:}
      The name is used as a technology, methodology, or generic
      English word rather than as the architectural component.
      An important exception preserves links when a component is
      \emph{named after} a technology---any sentence describing that
      technology's capabilities is about the component.
\end{enumerate}

\noindent If neither rejection pattern applies, the link is kept.
Structural guardrails ensure multi-word names and CamelCase
identifiers are never treated as generic words, and that interaction
sentences (``X sends data to Y'') produce links for all
participating components.

\subsubsection{Evidence Filter}\label{sec:evidence-filter}

\emph{Challenge~(C4):}
Even after boundary filtering, some links may remain where the
LLM hallucinated a reference that does not actually appear in
the sentence text.

\emph{Insight:}
If the component name or alias appears verbatim in the
sentence, the link cannot be a hallucination.
Links without such textual grounding that also lack
extraction-time verification are the only remaining
hallucination risk.

\emph{Design:}
A deterministic filter requires textual grounding: a link is
retained only if the component name or a known alias appears as a
word-boundary match in the sentence, or the link originates from a
strategy that already verified the reference at extraction time
(explicit extraction, anaphoric resolution).
Links that satisfy neither condition are removed.
This filter uses no LLM calls and serves as a final
deterministic check against ungrounded LLM outputs.
