\section{Research Design}
In this paper, we investigate whether we can find and predict \acl{ASI} issues.
Our research design focuses on three aspects of \ac{ASI} issues: their prevalence (\ref{RQ1 Smell traceability}), predictability (\ref{RQ2 Performance comparison} \& \ref{RQ3 Tempral availiabilty}), and transferability (\ref{RQ4 Cross project}).

\label{s:research_design}


\subsection{Research Questions}
\begin{enumerate}[leftmargin=*, labelindent=0em, label=\textbf{RQ\arabic*}:, ref=RQ\arabic*, series=researchQuestions]
    \item \label{RQ1 Smell traceability} \emph{How many evolved architectural smells can be \textbf{traced} to issues?}
\end{enumerate}
\emph{\textbf{Motivation:}} Before attempting prediction, it is important to understand the empirical evidence of smell evolution:
How many evolved smells can be traced back to issues?
Quantifying this clarifies the feasibility of issue-related analysis of architectural decay.
\begin{enumerate}[leftmargin=*, labelindent=0em, label=\textbf{RQ\arabic*}:, ref=RQ\arabic*, series=researchQuestions, resume]
    \item \label{RQ2 Performance comparison}  \emph{How do different predictors \textbf{perform} in finding architectural smelly issues?}
\end{enumerate}
\textbf{\emph{Motivation:}} Even if architectural smell changes can be linked to issues, it remains unclear whether such issues contain enough distinctive linguistic signals for detection. % semantic signals after labels
If they do, different learning algorithms may capture different aspects of the characteristics of smell-inducing issues.
Understanding which predictor performs well provides actionable insights for future algorithm enhancement and tool development.

    \item\label{RQ3 Tempral availiabilty}  \emph{How does the temporal availability of information influence the performance of \ac{ASI} issue prediction?%What is the influence of information \textbf{availability} on smelly issue prediction?
          } %if we include discussion or not, if temporal,
\end{enumerate}
\textbf{\emph{Motivation:} }
Issue discussions evolve over time as more comments and details accumulate.
The later we look in the issue’s timeline, the more information becomes available.
The earlier we look, the more useful the prediction can be for triggering timely architectural alarms.
Ideally, we want to predict smell-inducing issues at issue creation time.
However, if it improves performance, incorporating information from early pre-implementation discussions may also be beneficial.

\begin{enumerate}[leftmargin=*, labelindent=0em, label=\textbf{RQ\arabic*}:, ref=RQ\arabic*, series=researchQuestions, resume]
    \item \label{RQ4 Cross project} \emph{What is the \textbf{cross-project} prediction performance?}
\end{enumerate}
    \textbf{\emph{Motivation:}}
    When new projects start, it may lack sufficient historical data for training supervised models.
    A useful model should generalize beyond the project on which it was trained.
    Cross-project evaluation can also tell us to what degree smell-related linguistic patterns are general or project-specific.

\subsubsection{Experiments for RQ1}
To answer \ref{RQ1 Smell traceability}, we perform smell detection, linking and quantification on our datasets:
\paragraph{Smell evolution extraction}
For each project, we apply the architectural smell detection tools \ARCADE \cite{schmittlaser_ARCADEExtensible_2020} and \Arcan \cite{fontana_2017}. %their release of versions.
We detect smell evolution between consecutive release versions and record the affected architectural components and files.
For \Arcan-based detection results, we use its ASTracker\footnote{\url{https://github.com/darius-sas/astracker}} plugin to obtain smell evolution results.
For \ARCADE results, we implement an evolution analyzer, which can be found in our replication package\cite{replication}. We set the Jaccard similarity threshold (\autoref{eq:jac}) to 0.3.
This value is lower than ASTracker's default, as \ARCADE recover high-level components from files, but \Arcan operates at package/class level.
Therefore, with the default threshold, \ARCADE components will result in less match.

\paragraph{Architectural smell-inducing issue annotation}
From our collected data, we use explicit trace links provided by the GitLab platform to associate commits with issues.
Therefore, issues under consideration are those linked with at least one commit.
We set the smell-issue overlap threshold $\gamma$ to 0, meaning we include any non-zero smell-issue involvement as defined in \autoref{eq-overlap-si}.
Based on our approach, commits/issues linked with at least one smell will be marked as smell-inducing, while remaining issues are marked as non-smelly.
\paragraph{Quantification}
We compute:
\begin{enumerate*}[label=(\roman*)]
    \item the number and proportion of smell changes that are linked to issues,
    \item how many issues are smell-inducing vs.\ how many aren't.
\end{enumerate*}

The outcome of \ref{RQ1 Smell traceability} is a characterization of the prevalence and nature of issue-linked smell evolution.
It provides the target class distribution for the prediction tasks in \ref{RQ2 Performance comparison} \& \ref{RQ3 Tempral availiabilty}.

\subsubsection{Experiments for RQ2}
For \ref{RQ2 Performance comparison}, we regard predicting \acl{ASI} issues as a binary classification task.
We consider the issues labeled as smell-inducing by the two smell detectors (\ARCADE \& \Arcan) separately, as they can identify different smells and are applicable to different projects.
We evaluate multiple embedding models for each supervised classifier:
For TF-IDF encoding, we conduct standard data cleaning such as stemming and set the max-vocabulary size to 50,000.
For \ac{SBERT} embeddings, we use \textit{sentence-transformers/paraphrase-mpnet-base-v2}.
For OpenAI embeddings, we use the \textit{text-embedding-3-small} model.
The hyperparameters for the supervised classifiers are shown in \autoref{tab:ml-hyperparameters}.
We include a random baseline that predicts labels based on the smell frequency in the data.

We perform two runs of a five-fold cross-validation with train, test splits of $80\%, 20\%$.
We report average precision, recall, and F\textsubscript{1}-scores across the runs and folds.
Additionally, we conduct a Wilcoxon signed-rank test to compare against a random baseline, which predicts based on frequency.

Unlike typical classification setups, we define a successful identification only as correctly identifying positive samples, i.e., finding an \ac{ASI} issue.
This focus is both most relevant to developers and also the most challenging setting.
As \autoref{tab:overlap} shows, only a small percentage of issues are actually \ac{ASI} issues.
Because non-\ac{ASI} issues dominate the dataset, predicting the negative class is comparatively easy, and high performance on non-\ac{ASI} issues can be achieved even with simple baselines.
Including such metrics and averaging over both classes would yield good-looking but misleading results, as the overall scores would be dominated by the majority non-\ac{ASI} class.
Therefore, for \ref{RQ2 Performance comparison} we report precision, recall, and F\textsubscript{1}-score with respect to the positive (\ac{ASI}) class only.

\subsubsection{Experiments for RQ3}
This research question investigates how the different availability of information impacts the prediction performance of \acl{ASI} issues.
We evaluate the same task as in \ref{RQ2 Performance comparison} but under two different temporal conditions:
\begin{enumerate}
    \item \emph{Condition C\textsubscript{0}: No discussion (planning-only).}
          The model sees only the issue title and description (used in \ref{RQ2 Performance comparison}).
          This approximates the situation at issue creation, before any discussion.
    \item \emph{Condition C\textsubscript{jit}: Just-in-time information.}
          The model additionally sees comments that were posted \emph{before} the creation of the first related merge request.
          This simulates a decision point where implementation is about to start.
          Our prediction here can give hints to developers about architectural aspects to consider during implementation.

\subsubsection{Experiments for RQ4}
For RQ4, we examine ArchGuard's generalizability across projects:
We use the same supervised model settings as \ref{RQ2 Performance comparison}.
Instead of within-project cross-validation, we perform leave-one-project-out evaluation.
The idea is that for data from the same smell detector, we keep one project out for test, and do train and validation completely on the remaining projects.
For example, for ASI issues detected with \ARCADE, we use all issues of Shepard as a test, and train on Inkscape and StackGres issues.

\label{sec:dataset}
We build our dataset from GitLab-hosted projects.
GitLab provides first-class explicit linking between issues, merge requests (MRs), and commits.
This makes it straightforward to reconstruct issue-MR-commit traces.
For the selection of projects, we target large, production-grade systems that are actively maintained over multiple years and used by users in practice.
In this paper, we selected three projects:
\begin{enumerate}[leftmargin=*]
    \item \textit{Inkscape}\footnote{\url{https://gitlab.com/inkscape/inkscape}} is a widely used, free, and open-source vector graphics editor available for various operating systems.
          It has a large user and contributor base and a long release history since its initial release on November 6, 2003.
          Note that, as it migrated from other VCS platforms, GitLab only captures its development in recent years.
    \item \textit{StackGres}\footnote{\url{https://gitlab.com/ongresinc/stackgres}}, a Kubernetes operator for PostgreSQL that automates provisioning and observability of Postgres clusters.
    \item \textit{Shepard}\footnote{\url{https://gitlab.com/dlr-shepard/shepard}} is an actively maintained, open-source multi-database system for heterogeneous research data and provides a consistent API to work with the stored data.
\end{enumerate}

\autoref{tab:dataset} summarizes the collected artifacts per project.
Across the three systems, we analyzed 37 releases, totaling 7,715 issues, and 4,664 MRs.
