\subsection{Experiment Design}
\label{sec:exp-design}

To answer the four research questions we run four families of experiments on the same dataset (\autoref{sec:dataset}).

\subsubsection{Experiments for \ref{RQ1 SOTA comparison} -- Comparison to Existing Approaches}
\label{sec:exp:rq1}

We run two evaluations on the same five projects (\autoref{sec:dataset}):
\begin{enumerate}[leftmargin=*]
    \item \emph{Doc-to-model.} For every sentence in the architecture document, we use \approach to link it back to architectural components.
     We then compare recovered links with the doc-to-model gold standard links. 
    We compare \approach{} with \emph{SWATTR}~\cite{swattr}, the lexical NLP pipeline by string similarity and with \emph{LiSSA}~\cite{lissa}, a recent \ac{LLM}-based link recovery tool. 
    This is the link task where \approach{} can directly show its strength.
    \item \emph{Doc-to-code.} For every sentence we recover the code files it talks about and compare them with the file-level gold standard. 
    \approach{} reaches code files using a transitive linking approach, , the same composition used by TransArc.
    It combinines its doc-to-model links with the architecture model's component-to-file mapping. 
    We compare \approach{} with \emph{TransArc}~\cite{transarc}, the strongest published end-to-end pipeline on this benchmark, 
    and with \emph{LiSSA} as an \ac{LLM} baseline.
\end{enumerate}
For each task we use the same metrics \emph{TransArc} and \emph{LiSSA} use. 
We report link level precision, recall, and \fone per project and averaged across projects (both macro and micro).
The outcome of \ref{RQ1 SOTA comparison} tells us whether \approach{} improves over existing tools on the link task it targets directly (doc-to-model) and on the downstream task that developers care about (doc-to-code).

\subsubsection{Experiments for \ref{RQ2 metrics} -- Architecture-Driven Metrics}
\label{sec:exp:rq2}

The metric suite from \autoref{sec:metric:suite} is validated in the pre-study in \autoref{sec:metric:prestudy},
where two naive baselines (a Top-3 baseline per task and a random baseline) confirm that per-component \fone, sentence coverage, and noise rate each carry information the standard link-level \fone\ does not.
Here we apply the validated suite to \approach{} and the doc-to-code baselines (TransArc, LiSSA) from \ref{RQ1 SOTA comparison}, and to \approach{} and the doc-to-model baselines (SWATTR, LiSSA).
%TODO lissa rep not finished yet

For each (system, project, task) cell we recompute the four primary metrics: file-level \fone, per-component \fone, sentence coverage, and noise rate. We report per-project values plus macro means. Per system we provide two diagnostic views:
\begin{enumerate}[leftmargin=*]
    \item a \emph{per-component \fone\ distribution}, showing which components are fully covered, which are uncovered, and where false-positive and false-negative mass concentrates;
    \item a \emph{per-sentence coverage--noise scatter}, splitting gold sentences into served-cleanly, served-noisily, and unserved, with the share of each reported per system.
\end{enumerate}
Across systems and projects we report the rank correlation between file-level \fone\ and each other primary metric.
A metric that reorders the systems carries information that file-level \fone\ does not.
The appendix (\autoref{tab:rq2-redundancy}) additionally reports the coverage--purity composite (HUS) and the skill score (NDG); on our four-system, five-project grid both track metrics already in the main panel (HUS $\rho{=}{+}0.92$ with per-component \fone; NDG $\rho{=}{+}0.85$ with file \fone) and do not reorder any system pair beyond what the main panel already produces, so they are excluded from \autoref{tab:rq2-summary}.

\emph{\textbf{Expected outcome.}}
We commit to two falsifiable predictions:
\begin{enumerate*}[label=(\roman*)]
    \item per-component \fone\ reorders systems compared to file-level \fone, because file-level \fone\ is dominated by enrolment-inflated large components;
    \item noise rate varies independently of \fone---two systems with similar \fone\ can show markedly different per-sentence noise profiles.
\end{enumerate*}
The outcome of \ref{RQ2 metrics} is the table of (system, metric, project) values, the diagnostic plots, the rank correlations, and a verdict on each prediction.

\subsubsection{Experiments for \ref{RQ3 validators} -- Validator Contribution}
\label{sec:exp:rq3}
We build three ablations of \approach{} that remove validators while keeping the linker agents in place. We compare each ablation against \emph{\fullVariant{}}, the full pipeline.

\begin{enumerate}[leftmargin=*]
\item \emph{\noEntityValid{}}: skip the entity validator (Phase 4 in \autoref{sec:approach}); accept all candidates from the entity extractor without the p1 \ensuremath{\wedge} p2 evidence gate.

\item \emph{\noCitation{}}: skip the coreference / citation validator; accept all coreference candidates without the quoted-antecedent gate.

\item \emph{\noValidator{}}: skip both validators (the two above combined).
\end{enumerate}

Consensus voting in the entity extractor (the two-pass intersection at \autoref{sec:approach}) is kept inside \fullVariant{} as part of the extractor and is not ablated separately; reconstructing a no-consensus counterfactual would require new LLM calls and is out of scope.


For each variant we measure the four primary metrics (file-level \fone, per-component \fone, sentence coverage, and noise rate) and we contrast the difference with the cost in extra \ac{LLM} calls
(mean tokens per project), since the entity validator's two-pass p1 \ensuremath{\wedge} p2 evidence pattern roughly doubles entity-validation calls — not the entity-extraction calls themselves, which are a separate two-pass step inside the extractor and are included in the \fullVariant{} baseline cost.
The outcome of \ref{RQ3 validators} shows how much the validators contribute beyond the raw retrieval power of the agents, and
at what cost.

\subsubsection{Experiments for \ref{RQ4 ablation} -- Per-Agent Ablation}
\label{sec:exp:rq4}

We measure each linker by leave-one-out ablation across the two linkers: \linkerB{} (entity) and \linkerC{} (coreference).
The knowledge layer (\autoref{sec:approach}) stays in place in every run, because both linkers read from it.
For each variant we report:
\begin{enumerate*}[label=(\roman*)] \item the change in macro \fone over the
five projects, \item the change in sentence coverage and noise rate, which tells
us whether the removed agent added recall or only filtered false positives, and
\item how many true positives are lost that no other agent recovers.
\end{enumerate*} Set overlap is reported via the UpSet decomposition |only_E|, |both|, |only_C| in \autoref{fig:rq4-upset}; per-linker unique-TP counts in \autoref{tab:rq4-agents}.


\subsection{Dataset}
\label{sec:dataset}

We use the ardoco benchmark, the largest architectural traceability benchmark to the best of our knowledge\cite{}.
It contains five Java open-source systems with hand-curated architecture docs, an architecture model, and a gold standard at two grains, sentence-to-component and sentence-to-file:
\emph{MediaStore}, \emph{TeaStore}, \emph{Teammates}, \emph{BigBlueButton}, and \emph{JabRef}.
We use this benchmark because it is the standard evaluation set for this task~\cite{transarc,lissa}.

\input{table/dataset-stat}

\autoref{tab:dataset} lists, per project, the number of sentences in the architecture document, the number of components in the architecture model, the number of code files, the number of human gold decisions, and the number of link-level pairs after each directory decision is expanded to its files.
The expansion factor differs by two orders of magnitude across projects (1.0$\times$ for MediaStore, 217.6$\times$ for JabRef).
This is one of the reasons we report the extra metrics in \ref{RQ2 metrics}.

For each project we use the architecture document as input~$D$, the architecture model as the component set~$C$, and the gold standard as the ground-truth links between sentences of~$D$ and components of~$C$ (or files belonging to components of~$C$, for the doc-to-code task).
We use the official benchmark loaders for $D$ and $C$ to stay aligned with prior work.
