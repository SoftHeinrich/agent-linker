\section{\approach}\label{sec:approach}

This section presents \approach, a training-free pipeline that
recovers trace links from an architecture document to the components
of an architectural model.
Given a document~$D$ with sentences $S = \{s_1, \ldots, s_n\}$ and a
component set $C = \{c_1, \ldots, c_m\}$, \approach outputs a link set
$L \subseteq S \times C$, where each link $(s_i, c_j)$ asserts that
sentence~$s_i$ discusses the architectural responsibilities, behaviour,
or interactions of component~$c_j$.

Trace links are, by definition, anchored on a textual reference to the
linked component: the linked sentence has to mention the component in
some form.
The dominant form is the canonical component name itself --- when a
document discusses \texttt{EventDispatcher}, the most common
documentary act is to write ``EventDispatcher.''
The remaining sentences refer to the same component through one of two
oblique forms: a project-specific alias (i.e., an abbreviation, a
synonym, a partial name, or a functional role) or a discourse pronoun
(\emph{it}, \emph{this}, \emph{their}, $\ldots$), and these two forms
together account for a long tail of the gold
links.\todo{cite empirical distribution from RQ4: $\sim$70\% canonical,
$\sim$25\% alias, $<$5\% pronoun}
Two facts complicate this otherwise direct picture.
First, component names are often ordinary technical English
(\texttt{Core}, \texttt{Adapter}, \texttt{Logic}, \texttt{Storage}),
so a surface-level lexical match overshoots into generic uses of those
words.
Second, project-specific aliases are not known in advance, so any
linker that targets the long-tail reference forms must first discover
them at runtime.

\approach resolves these complications in three stages.
\textbf{Project knowledge discovery} (Tier~1, \S\ref{sec:knowledge})
learns, at runtime, which component names are ambiguous and which
document terms are aliases for which components.
\textbf{\linkerA} (Tier~2, \S\ref{sec:anchor}) recovers the
majority of trace links by exploiting the most direct evidence
permitted by the trace-link definition --- canonical component
mentions --- and uses the learned knowledge to prune false-positive
name matches.
The \textbf{supplementary linkers} (Tier~2, \S\ref{sec:supplementary})
close the residual gap left by \linkerA: \linkerB recovers alias-based
references and \linkerC recovers pronoun-based references.
Tier~3 (\S\ref{sec:merge}) consolidates the three sources into a
single de-duplicated link set.
To the best of our knowledge, \approach is the first trace-link
recovery pipeline that combines runtime architectural-knowledge
discovery, a definition-driven primary linker, and evidence-grounded
supplementary linkers for architecture-document-to-model tracing.

\subsection{\approach in a Nutshell}\label{sec:nutshell}

\approach is organised as a three-tier directed acyclic graph
(Figure~\ref{fig:pipeline}).
As illustrated in Figure~\ref{fig:pipeline}, \approach proceeds in
three steps:
(i)~three independent Tier-1 analyses, run in parallel, produce a
\emph{model ambiguity map}, a \emph{document alias table}, and a
raw \emph{anchor set} of canonical-name mentions;
(ii)~\linkerA disambiguates those raw mentions against the
ambiguity map, while \linkerB and \linkerC --- both supplementary ---
target the references \linkerA cannot see;
(iii)~the three validated link sets are merged by priority-ordered
deduplication.
The fan-out/fan-in structure is deliberate: every expensive LLM call
whose inputs are independent runs in parallel, thereby keeping the
latency of the pipeline within a single round-trip per project
regardless of how many linkers participate.

Two design rules cut across all three tiers.
\textbf{Consensus for open-ended extraction.}
Where the LLM may hallucinate candidates, \approach runs two
independent passes and keeps only candidates on which both passes
agree --- except for exact canonical-name matches, whose evidence
appears verbatim in the sentence and need not be intersected.
\textbf{Evidence for validation.}
Where a decision can be checked against the document, \approach
requires the LLM to expose the evidence it used --- matched spans,
mention types, anchor sentences, or antecedent sentence numbers ---
so that a deterministic check, rather than a second opaque LLM call,
decides acceptance.

\subsection{Project Knowledge Discovery}\label{sec:knowledge}

Tier~1 builds the project-specific vocabulary the downstream linkers
need.
Its three analyses are mutually independent, so \approach runs them
concurrently and emits three outputs: an \emph{ambiguity map} over
the component set, an \emph{alias table} over the document, and a
raw \emph{anchor set} of canonical mentions ready for
disambiguation.
The first two outputs are described in this subsection; the third is
the input to \linkerA and is described together with it in
\S\ref{sec:anchor-extraction}.

\subsubsection{Model Understanding}\label{sec:model-understanding}

The model-understanding analyser asks a single question of the
component list: which component names can be confused with ordinary
technical English?
A sentence containing the word ``storage,'' for example, does not
necessarily refer to a component named \texttt{Storage}; it may
describe a general storage concern.
We submit the component list to a few-shot LLM classifier that splits
the names into \emph{architectural} names (unambiguous identifiers
such as \texttt{TaskScheduler}) and \emph{ambiguous} names
(single-word identifiers that double as general vocabulary,
e.g., \texttt{Core}, \texttt{Logic}).
A structural filter keeps only single-word, lowercaseable names in
the ambiguous bucket, so that CamelCase compounds, multi-word names,
and acronyms are never classified as generic merely because their
sub-words are common.
The ambiguity map is consumed by both \linkerA (whose per-component
disambiguator embeds the classification in its dossier) and \linkerB
(whose generic-word precheck applies only to ambiguous names),
thereby giving every downstream linker the same view of which names
need careful handling.

\subsubsection{Document Understanding}\label{sec:doc-understanding}

The document-understanding analyser learns the project-specific
vocabulary that the document uses to refer to components.
It builds an \emph{alias table} whose entries map an observed term
to a canonical component and label the term as either \emph{global}
(safe to recognise anywhere in the document, e.g., a parenthetical
abbreviation or a CamelCase identifier) or \emph{local} (a single
lower-case word whose referent depends on the surrounding context).

\textbf{Alias extraction.}
A first LLM pass scans the document and proposes two kinds of
mappings: \emph{abbreviations} (short forms introduced by the text,
e.g., ``Abstract Syntax Tree (AST)'') and \emph{synonyms}
(alternative names that identify exactly one component, including
trailing words of multi-word component names when the document uses
the trailing word alone).
The prompt asks for an alias scope; the scope is load-bearing
because \linkerB (\S\ref{sec:contextual}) receives only the global
subset, thereby preventing a generic local word from being broadcast
into every sentence as if it were a project-wide name.

\textbf{Alias judging.}
A second LLM pass judges the proposed mappings with an
approval-biased rubric.
The rubric approves abbreviations formed from a component's
initials, unshared trailing words of multi-word names, CamelCase
identifiers, and multi-word phrases containing the component name;
it rejects only terms that are clearly generic, clearly name a
different component, or clearly refer to the whole system.
The asymmetry is deliberate: a falsely rejected alias permanently
removes a possible reference form, while a falsely approved alias
can still be filtered by Tier~2 validation.

\subsection{\linkerA: The Primary Linker}\label{sec:anchor}

The first observation behind \approach is that, by the definition of
a trace link, the linked component must be present in the linked
sentence in some form.
The simplest such form --- and, on every benchmark project we
inspected, the most frequent\todo{cite RQ4 breakdown} --- is the
canonical component name itself.
\linkerA exploits this property directly: it recovers the trace links
whose evidence is the canonical name, and only those links.
It is therefore primary, not in the sense that it runs first
(the supplementary linkers run in parallel with its disambiguator),
but in the sense that it carries the largest share of recall and
that the supplementary linkers are sized against the gap it leaves.

\linkerA is split into two stages: a Tier-1 \textbf{extractor} that
operates without any learned knowledge, and a Tier-2
\textbf{disambiguator} that operates once the ambiguity map and alias
table are available.
Splitting the two stages lets the extractor run concurrently with
knowledge discovery while still permitting knowledge-aware filtering
before any link is emitted.

\subsubsection{Anchor Extraction}\label{sec:anchor-extraction}

Two complementary LLM passes scan the document in batched
segments.
The \textbf{mention-framed pass} asks which components are
explicitly mentioned or referenced in each sentence.
The \textbf{actor-framed pass} asks which components are
architecturally relevant to the sentence --- that is, whose role,
behaviour, interaction, or responsibility is being described.
The two passes are merged asymmetrically.
Exact canonical-name matches from \emph{either} pass are accepted,
because the evidence appears verbatim in the sentence and the
dominant risk is a missed mention.
Non-exact matches, such as synonyms or partial names, are accepted
only when \emph{both} passes agree.
The asymmetric vote preserves recall on direct mentions and uses
intersection to suppress hallucinated non-exact references,
thereby emitting a raw anchor set that is high precision even
before any learned knowledge is applied.

\subsubsection{Anchor Disambiguation}\label{sec:anchor-disambig}

Raw anchors are high precision but blind to project-specific
ambiguity: a sentence containing the word ``logic'' may discuss the
\texttt{Logic} component, may describe generic program logic, or
may refer to a code path that shares the name.
The disambiguator revisits each raw anchor with a
component-specific \emph{dossier} containing four elements:
(i)~the component's ambiguity classification and its known aliases
from Tier~1;
(ii)~up to five \emph{anchor sentences} elsewhere in the document
where the component name appears in proper-case standalone form,
serving as calibration examples of confirmed reference;
(iii)~each raw anchor case with its preceding sentence and a
\emph{mention type} (proper-case standalone, lower-case,
dotted-path occurrence, alias, or unclear indirect match);
(iv)~a runtime-generated decision rubric of four to six items,
built by a separate LLM call from the document and the component
list using a generic compiler-style example as the rubric shape.

The runtime rubric is the only document-specific element of the
prompt: it captures regularities that vary between projects --- in
some documents component names appear mostly as grammatical actors,
in others mostly in configuration or interface descriptions --- and
replaces a static rubric that cannot accommodate these differences.
For each raw anchor case, the LLM returns \textsc{component} when
the sentence discusses the architectural component, and
\textsc{other} when the name carries a different meaning (a code
path, an algorithmic technique, an embedded sub-entity, a different
entity, or a generic English word).
The prompt is approval-biased because the raw anchors have already
passed asymmetric voting; if the rubric builder returns no rubric
after two attempts, the implementation fails rather than silently
falling back to a static rubric, thereby keeping every emitted
\linkerA link attributable to the intended runtime-rubric design.

\subsection{Supplementary Linkers}\label{sec:supplementary}

A trace link whose evidence is not a canonical component name is,
by construction, invisible to \linkerA.
Two reference forms produce such links.
First, the sentence may refer to the component through a
project-specific alias --- an abbreviation, a synonym, a partial
name, a functional role, or a prepositional mention such as
``handled by'' or ``via.''
Second, the sentence may refer to the component pronominally
(\emph{it}, \emph{this}, \emph{these}, \emph{their}, $\ldots$),
with no component name or alias present at all.
\linkerB and \linkerC are sized to exactly these two gaps, and each
is therefore narrower in scope than \linkerA.

\subsubsection{\linkerB: Alias and Role References}\label{sec:contextual}

\linkerB recovers alias-based and functional references using the
global alias table from \S\ref{sec:doc-understanding}.

\textbf{Dual-pass extraction.}
The same broad extraction prompt is run twice independently.
Each pass receives the component list and the global alias table,
and each proposed candidate must name a valid component, point to
an existing sentence, and provide a matched text span that appears
in that sentence.
\approach keeps only the intersection of the two passes; using the
same prompt twice avoids mixing prompt-specific biases, so the
residual disagreement reflects only LLM non-determinism.

\textbf{Evidence bundles.}
Before validation, \approach attaches an evidence bundle to each
candidate.
The bundle records the matched span, the mention type, the
preceding sentence, up to five anchor sentences with confirmed
standalone component mentions, the ambiguity flag for the
component, and the extraction rationale.
Validation therefore sees not only a sentence and a component name
but also \emph{why} the proposer believed the link was plausible.

\textbf{Generic-word precheck.}
For ambiguous components whose candidate mention appears only in
lower-case form, \approach first asks whether the word is being
used as a component reference or as ordinary English.
Only candidates classified as component references continue to the
main validation step.
If the precheck cannot parse a clear answer, \approach keeps the
candidates, thereby preserving the recall-first behaviour used
throughout the pipeline.

\textbf{Two-pass validation.}
Remaining candidates are judged by two independent validation
passes with complementary foci.
The first pass checks \emph{architectural participation}: does the
sentence name the component as a participant that performs an
operation, provides a service, is configured, or takes part in
system behaviour?
The second pass checks \emph{referential specificity}: does the
mention identify this specific architectural element rather than a
generic technical term?
A candidate is accepted only when both passes approve it.
The intersection is stricter than \linkerA's disambiguation because
\linkerB deliberately starts from a larger and noisier candidate
space.

\subsubsection{\linkerC: Pronominal References}\label{sec:coref}

\linkerC targets sentences whose evidence is a pronoun:
\emph{it}, \emph{they}, \emph{this}, \emph{these}, \emph{that},
\emph{those}, \emph{its}, and \emph{their}.
Each pronoun-bearing sentence is presented with a $\pm5$-sentence
context window, with the target sentence marked explicitly.
The LLM returns only the resolutions it is certain about and, for
each resolution, must cite the target sentence, the pronoun, the
component, the antecedent sentence number, and the antecedent
quote.

\approach then verifies the cited antecedent deterministically.
For canonical-name antecedents, the antecedent sentence must
contain a standalone mention of the component name.
For alias-based antecedents, the LLM must explicitly mark the
antecedent as alias-based, in which case the alias-table lookup
provides the same deterministic check.
Only resolutions surviving these checks become \linkerC trace
links.
Citation grounding therefore removes any antecedent the LLM may
have fabricated, thereby reducing pronoun resolution from an
open-ended reasoning task to a deterministic verification.

\subsection{Link Consolidation}\label{sec:merge}

Tier~3 is intentionally simple.
\linkerA, \linkerB, and \linkerC have each applied their own
acceptance rules, so consolidation does not reinterpret their
evidence.
\approach concatenates the three link sets and removes duplicate
sentence--component pairs in a fixed priority order: \linkerA
first, \linkerB second, \linkerC third.
The priority preserves the most direct evidence whenever multiple
linkers recover the same pair and reflects the linker hierarchy ---
\linkerA is primary by the trace-link definition itself, while the
supplementary linkers contribute the pairs that \linkerA, by the
same definition, cannot find.

The final output is a documentation-to-model trace-link set; these
links can be evaluated directly at the architecture level or
composed with existing model-to-code mappings to recover
documentation-to-code traces (\S\ref{sec:experiment}).
