## Design Constraints (v2.3 Hard Rules)

User-set hard rules carried forward from v2.2 close (2026-06-01):

1. **Static-prompt-elegance preserved** — Voyager linker style (frozen skeleton with named slots + injected rules, see `src/llm_sad_sam/linkers/experimental/s_linker13_skill_learned_clean.py` consuming `prompts_v3_axiom.py`) is the v2.3 architectural baseline. Prefer extension via slot-injection over inline prompt-body editing. New mechanisms register as named slot consumers, not as ad-hoc prompt rewrites. See `[[user-voyager-preference]]` memory.
2. **Backend policy: gpt-5.4 default; Claude only if super necessary** — All v2.3 probes, ranges, sweeps, ablations default to gpt-5.4. Claude runs require explicit justification (e.g. final pre-promotion GATE-01 cross-model floor proof on a brand-new canonical artifact). See `[[feedback-prefer-gpt-backend]]` memory. Per this rule, Sub-Question 3 below (Claude Probe D re-test) is **SKIPPED**, not parked as a v2.3 prep candidate.
3. **GATE-06 BENCHMARK_TABOO** continues. All LLM-generated content (rubrics, distilled rules, abstraction-style libraries) gets taboo-scanned before being persisted/cached.
4. **No hardcoded benchmark vocabulary** anywhere — prompts, helpers, code paths. v2.0 thesis dependency.

## Spike Candidates (v2.3 Exploration Seeds)

Two extension directions worth a /gsd:spike before v2.3 mainline commits to v4:

1. **Alias-rubric runtime injection** — Apply the Probe D pattern (one LLM call per (text_stem, comp_hash, backend, model) builds a per-document rubric, caches it, replaces a static prompt slot) to the `DOC_KNOWLEDGE_JUDGE_RULES` slot (alias judge). The alias judge is the highest-leverage rule-removal target after coref (Phase 12 distillation evidence). Static-prompt-elegance preserved — slot consumer pattern is identical to Probe D. Backend: gpt-5.4 only.
2. **Extraction-rubric runtime injection** — Same pattern applied to `ENTITY_EXTRACTION_RULES`. Extraction tier is upstream of judge, so a runtime extraction rubric could shift the FP/FN distribution before the judge ever sees a candidate. Higher risk (changes the candidate pool, not just the gate); cheaper to test (single sweep).

These spikes are ORTHOGONAL to Voyager v4 — they extend Probe D into adjacent slots while keeping the bank-based v4 work as the mainline. If both spikes STRONG_PASS, v2.3 could ship `s_linker14_min = s_linker13_min + 3 runtime rubrics (coref + alias + extraction)` with no Voyager bank at all, which sidesteps the split-fragility problem entirely. If they FAIL, Voyager v4 stays mainline and these are documented negatives.
