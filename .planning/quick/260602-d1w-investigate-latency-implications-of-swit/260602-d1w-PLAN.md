    Using public OpenAI documentation (knowledge cutoff Aug 2025 is sufficient — Flex tier
    launched mid-2025), characterize Flex tier and write FINDINGS.md.

    FINDINGS.md must cover these five sections:

    ## 1. What is Flex Tier?
    - Flex Processing is OpenAI's asynchronous batch API with up to 50% cost reduction.
    - Requests are queued and processed within a 24-hour window (no latency SLA).
    - The API is invoked via the Batch API endpoint (POST /v1/batches), not the standard
      /v1/chat/completions endpoint. Results are polled or retrieved after completion.
    - NOT a drop-in replacement for synchronous calls — requires a fundamentally different
      client architecture (submit → poll → retrieve).

    ## 2. Expected Latency: Flex vs Standard
    | Tier     | Latency per call | Cost multiplier |
    |----------|-----------------|-----------------|
    | Standard | ~2–8s (gpt-5.4) | 1.0x            |
    | Flex     | 1–24h per batch | 0.5x            |

    Note: "latency" for Flex is batch turnaround, not per-call. If 100 calls are batched,
    they complete together, not individually.

    ## 3. Training Loop Compatibility Analysis
    Describe the synchronous call chain in voyager_train_tlr_v5.py:

    - _run_linker_l waits for s_linker14_voyager.link() to return before computing FP/FN.
    - OD role consumes FP/FN from L result — cannot start until L completes.
    - Assessor role consumes proposed patterns from OD — cannot start until OD completes.
    - The outer pass loop (MAX_OUTER_PASSES=5) is sequential: pass N+1 starts only after
      pass N's bank has been updated with committed patterns.

    Verdict: The entire loop is a sequential dependency chain. Flex tier requires
    async submit/poll semantics. Retrofitting LLMClient.query() to use the Batch API
    would require:
      (a) A new LLMBackend.OPENAI_FLEX enum variant.
      (b) Batch submission at the start of each role's call cluster.
      (c) A polling loop (min ~10-min interval) before downstream roles can proceed.
      (d) Wall-clock training time for a probe run: from ~10–40 min (standard) to
          potentially 2–24h per outer pass, making 5-pass training take days, not hours.

    This is NOT a latency optimization — it is a latency multiplication by ~100–1000x
    in exchange for 50% token cost reduction.

    ## 4. Cost Impact
    Estimate current spend per tier using the $80 total budget cap from STATE.md:
    - Probe: ≤$10 at standard rates → ≤$5 at Flex rates.
    - Range: ≤$25 → ≤$12.50 at Flex rates.
    - Confirmation: ≤$60 → ≤$30 at Flex rates.
    - Total saving if all tiers used Flex: ≤$40 over the full v2.6 training run.
    - At gpt-5.4 pricing (~$10/M input, ~$30/M output), probe costs ~$2–5 in practice,
      meaning the absolute saving per run is small ($1–2.50 per probe).

    ## 5. Recommendation
    **DO NOT switch to Flex tier for v2.6 or v2.7.**

    Rationale:
    1. The training loop is a synchronous dependency chain. Flex tier would increase
       wall-clock time per training run from ~1 hour to potentially >24 hours, making
       iterative development infeasible.
    2. The absolute cost saving is small: ≤$40 over the entire v2.6 budget cap of $80.
       The engineering cost of retrofitting LLMClient + training loop exceeds this.
    3. Flex tier is appropriate for bulk offline jobs (e.g., pre-running linker over all
       5 datasets in parallel), not for interactive training loops where each pass
       depends on the prior pass's results.
    4. If cost becomes a concern in a future milestone, the right optimization is:
       (a) Better L-role caching (already implemented in _run_linker_l), OR
       (b) Running Flex-tier in a separate offline benchmark sweep (no training loop),
           not in the training loop itself.

    **C-6 deferral to v2.7+ is correct. Close C-6 as "investigated — not viable for
    synchronous training; defer offline-sweep use case to v2.8+."**

    Write the file using the five sections above. Populate the latency table with real

    characterization in Task 1.
