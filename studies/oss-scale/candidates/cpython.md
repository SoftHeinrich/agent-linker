## D2 — Component model

Three project-authored candidates, none at the granularity the prose uses:

**(a) Top-level directories** — `git ls-tree -d HEAD`: 20 entries (16 non-dot). Code dirs: `Objects Python Parser Modules Lib Include Programs Tools Grammar PC Mac PCbuild Platforms` (13). The devguide "Directory structure" section describes 14 of them in one line each (URL: https://devguide.python.org/getting-started/setup-building/#directory-structure). Too coarse: `Python/` alone is "the compiler, eval loop and various built-in modules", and 48 of the 118 path-bearing sentences point into it (Include 19, Parser 18, Grammar 12, Tools 12, Lib 8, Objects 7, Doc 4, Modules 2, PC 1).

**(b) Labels and experts index.** GitHub label API: 93 labels on python/cpython, of which 5 component labels (`stdlib`, `extension-modules`, `interpreter-core`, `docs`, `tests`; defined in `devguide/triage/labels.rst` as `Lib/`, `Modules/`, `Objects/+Python/+Grammar/+Parser/`, `Doc/`, `Lib/test/`), 33 `topic-*` labels, 10 `OS-*`. `devguide/core-team/experts.rst` (https://devguide.python.org/core-team/experts/): Stdlib table 109 module rows, Tools 3 rows, "Miscellaneous / Interest area" table 42 rows (counted lines starting in column 1 inside each table) = 154 rows mapping names to *people*.

**(c) CODEOWNERS** — `.github/CODEOWNERS`: 659 lines, 366 pattern lines, 85 distinct owner sets, 63 individual owners (parsed by `codeowners.py`). Patterns by prefix: Lib 128, Doc 61, `**` 35, Modules 31, Python 23, Tools 21, Include 20, Objects 14, Parser 3, InternalDocs 4. Owner sets are people, not named components.

**Name agreement with the prose** (sentence hits for each name, substring, case-insensitive): of the 42 experts interest areas, 24 hit >=1 sentence, but 'io' (738) and 'time' (73) are substring artifacts and 'context', 'runtime', 'core workflow', 'version control', 'issue tracker', 'documentation', 'object model' hit on generic words; the honest set is ~14: bytecode 61, memory (management) 72, threads 39, PEG parser 36, performance 23, JIT 18, import (machinery) 14, extension modules 12, Unicode 10, initialization 5, AST/compiler 4, frozen modules 3, symbol table 2, algorithms 2. `subinterpreters`, `pattern matching`, `f-strings`, `argument clinic` get 0. **Recommendation.** No single project-authored list is both the right size and the doc's vocabulary. The workable level is a **curated ~15-20-entry subset of the experts "Interest area" table restricted to the interpreter core** (AST/compiler, bytecode, PEG parser, JIT, memory management, object model, import machinery, frozen modules, symbol table, subinterpreters, initialization, threads, Unicode, extension modules, runtime, performance, argument clinic, f-strings, pattern matching, context) — project-authored names, but the *selection* is ours. For a fully mechanical, no-curation eval, use the 8-13 top-level dirs (D3 resolves paths to them exactly) and accept the `Python/` skew.

## T1 — Downstream task

(i) **Issue triage.** GitHub search API `repo:python/cpython is:issue label:X` (unauthenticated, one call per label): interpreter-core 10,899; stdlib 21,533; extension-modules 4,662; docs 11,860; topic-asyncio 1,632; topic-unicode 1,060; topic-IO 746; topic-free-threading 710; topic-typing 586; topic-JIT 317; topic-parser 198; topic-C-API 923; topic-subinterpreters 357; topic-importlib 244 (measured 2026-09-04; 3 of 14 calls needed a retry after a rate-limit). Gold is plentiful, but routing an *issue* to a label is a text-classification task on issue text; the doc-to-component links help only for issues that use InternalDocs vocabulary. Not a direct use of the links; skeptical.
(ii) **Doc staleness.** Spot check of 7 named functions in their named files at HEAD: `_PyEval_EvalFrameDefault` in Python/ceval.c (3 hits), `_PyAST_Compile` in Python/compile.c (2), `_PyFrame_ClearExceptCode` in Python/frame.c (1), `gen_send_ex2` in Objects/genobject.c (5), `MAGIC_NUMBER` in Lib/importlib/_bootstrap_external.py (4), `interned_strings` in Include/internal/pycore_runtime_structs.h (1), `_Py_asdl_generic_seq_new` (in `Include/internal/pycore_asdl.h`, the header compiler.md names alongside Python/asdl.c). Plus 84/84 paths and 84/89 identifiers resolving; the 3 genuine misses (present-tense sentences in compiler.md naming `PyArena_New/Free/AddPyObject`, renamed to `_PyArena_*`) are the **entire** staleness positive set at HEAD: 3 sentences in 1,551 (0.2%); a fourth candidate (`_PyDict_MaybeUntrack`) is a correct historical note and would be a false positive. InternalDocs is 15 months old and maintained, so at HEAD the task is nearly empty. A historical variant (doc snapshot at 2024-06 vs tree at 2026-09, or vice versa) would have to be constructed and was not measured.
(iii) **Doc-update recommendation.** Protocol: for each of the 35 co-change commits, hide the doc diff, feed the code files -> top-level dir / CODEOWNERS set -> component, rank InternalDocs sentences linked to that component, score hit@k against the changed doc lines (`git show --numstat`/`-p`). Gold size ~35 commits / 41 doc-file rows, 19 of them sentence-pinnable. Small but real and fully mechanical.

## K — Killer-case pitch

The CPython core team ships 1,551 sentences of maintainer-facing design prose in-tree and promises to keep it current; sentence-to-subsystem links would let a reviewer of any PR touching `Python/ceval.c`, `Parser/`, or `Python/gc.c` see exactly which paragraphs of the compiler/interpreter/GC design docs now need re-reading — at 10x the benchmark's sentence count, in the most widely used interpreter in existence.

## C — Cost / feasibility

Pairs: 1,551 x 8 dirs = 12.4k; x 20 curated areas = 31k; x 42 interest areas = 65k (vs. <=2.8k in the benchmark). Licence: PSF-2.0 for InternalDocs (in-tree, `LICENSE`), CC0 for devguide — both vendorable into the replication package with the licence text. All artifacts are git-tracked and fetchable by SHA; issue labels need the API. Sentence splitting of Markdown with inline code needs the custom splitter above (Markdown, not reST); 267 of 1,551 units are bullet fragments without terminal punctuation.

## Verdict

READY-WITH-WORK. Prose is ready (1,551 sentences, in-tree, maintained, PSF-licensed, 19% carrying code references), and mechanical gold exists (295 code-referencing sentences resolvable to dirs/owners, 35 co-change commits).
The work: the component list. No project-authored artifact matches the doc's granularity — top-level dirs are total but 41% of path sentences fall in `Python/`, CODEOWNERS covers 20-38% of core C files and is people-keyed, and only ~14 of 42 experts interest areas ever appear in the prose. Pick and defend a ~15-20 entry level before running; the staleness task has 3 positives at HEAD (one doc) and must be built from history if wanted.
